# Expansion hack data format: what pokeemerald-expansion builds look like from outside

Researched on 2026-11-12 against rh-hideout/pokeemerald-expansion (every release tag `expansion/0.9.0` to `expansion/1.17.2`, `master` at 1.17.3-dev, `upcoming` at 1.18.0-dev), its docs and GitHub releases, the public repositories of the hacks in section 5, and the source of third-party tools that read expansion hacks. No real hack ROM was opened.

Conventions. `derived` means I computed it from source text: host gcc on `struct GFRomHeader` with every pointer replaced by `uint32_t`, and `clang --target=arm-none-eabi -fdump-record-layouts` on lines 132-299 of `include/pokemon.h` at 1.17.2 with a stub prelude (`u8`/`u16`/`u32` typedefs, `min`/`max`, `POKEMON_NAME_LENGTH 12`, `PLAYER_NAME_LENGTH 7`, packed enums `Species`, `Item`, `Move`, `Type`). The Makefile builds with `-mabi=apcs-gnu`, clang used the default AAPCS rules, so a derived bit position is a reading of the source, not a measurement of a ROM. `unverified` means I could not trace the statement to a page I could read. Third-party tool notes show what those tools do and what their authors measured; they are not evidence of how a hack was built. PokeCommunity and PokeMon Coders returned HTTP 403 to automated fetches; I did not work around that, so every claim that rests only on a search-result excerpt of those pages is marked unverified.

## Findings at a glance

- A machine-readable marker exists: the 6-byte magic `RHHEXP` followed by major, minor, patch and a flags byte, since 1.7.0 (2023-12-17); from 1.8.0 (2024-03-17) it also carries move, species, ability and item counts, the item name length and a pointer to `gAbilitiesInfo`. It has no RAM address, stride or field offset. Builds before 1.13.0 can lack it (gc-sections), and at least one reported hack has none.
- The Pokémon struct (80 and 100 bytes, XOR encryption, 24 substruct orders, checksum) is unchanged in size and mechanism. Against vanilla the bit layout differs in two steps: already in the first tags (0.9.0/1.0.0: ball moved to Sub0, ability slot widened and moved) and from 1.8.0 (11-bit species, 10-bit item, 21-bit experience, 11-bit moves, 7-bit PP, tera type, hyper training, nickname chars 11-12, hidden nature, hp lost, shiny modifier). A smaller change landed in 1.9.0. From 1.9.0 through 1.17.2 the bit widths and positions are textually identical.
- Type IDs shifted in 1.9.0 (`TYPE_NONE` 255 to 0, `TYPE_NORMAL` 0 to 1). `gPlayerParty` and `gEnemyParty` were replaced by `gParties[4][6]` in 1.16.0. `BattlePokemon.status2` became a macro-generated `volatiles` bitfield struct in 1.13.0, and that field list changed in 9 of the 21 tag steps from 1.13.0 to 1.17.2.
- `make` writes `pokeemerald.elf` and `pokeemerald.map` by default. `make syms` writes `pokeemerald.sym`. DWARF needs `make debug` or `DINFO=1`. The `.gba` is `objcopy -O binary` of the ELF, so it carries no symbols. Expansion publishes no symbol file for any tag; pret does for vanilla.
- Named hacks with public source: Pokémon Emerald Rogue (its `expansion` branch is on expansion 1.7.4, with its own mon layout), Elite Redux (not expansion; its own unencrypted mon struct), Inclement Emerald (RHH feature-branch lineage that predates the 1.7.0 header, own layout). Run & Bun, Emerald Imperium and Lazarus: no public game source found. No named hack publishes symbols.
- Existing tools do not rely on symbols from the hack. pokedaisy builds the matching expansion tag as a reference and matches addresses through literal pools. BananaLinux finds everything from the ROM at open time. Run & Bun scripts hard-code addresses.

## 1. Version marker in the ROM

### 1.1 The RHH header

`src/rom_header_rhh.c` defines `struct RHHRomHeader`, placed in its own linker section. [master](https://github.com/rh-hideout/pokeemerald-expansion/blob/master/src/rom_header_rhh.c). Source comment: "we should only ever append data to the end"; the magic is "Useful to locate the header if it shifts."

| Offset | Field | Content | First release |
|---|---|---|---|
| 0x00 | `rhh_magic[6]` | ASCII `RHHEXP` | 1.7.0 |
| 0x06 | `expansionVersionMajor` | u8 | 1.7.0 |
| 0x07 | `expansionVersionMinor` | u8 | 1.7.0 |
| 0x08 | `expansionVersionPatch` | u8 | 1.7.0 |
| 0x09 | `expansionVersionFlags` | u8; bit 0 = `EXPANSION_TAGGED_RELEASE` | 1.7.0 |
| 0x0A | `movesCount` | u16, `MOVES_COUNT` | 1.8.0 |
| 0x0C | `numSpecies` | u16, `NUM_SPECIES` (equals the egg's species ID, `SPECIES_EGG = NUM_SPECIES`) | 1.8.0 |
| 0x0E | `abilitiesCount` | u16 | 1.8.0 |
| 0x10 | `abilities` | pointer to `gAbilitiesInfo` | 1.8.0 |
| 0x14 | `itemsCount` | u16 | 1.8.0 |
| 0x16 | `itemNameLength` | u8, `ITEM_NAME_LENGTH` | 1.8.0 |
| 0x17 | `padding` | u8 | 1.8.0 |

- 1.7.0 has only the first 10 bytes: [1.7.0 file](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.7.0/src/rom_header_rhh.c). 1.8.0 has the 24-byte form: [1.8.0 file](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.8.0/src/rom_header_rhh.c). I diffed the struct at all 52 tags that contain the file: 1.8.0 through 1.17.2 are byte-identical in layout; 1.14.0 only renames `struct Ability` to `struct AbilityInfo`.
- Release notes: 1.7.0 "Added expansion Rom Header ... Added defines for Expansion version number" ([1.7.0 changelog](https://github.com/rh-hideout/pokeemerald-expansion/blob/master/docs/changelogs/1.7.x/1.7.0.md), line 69, [PR 3454](https://github.com/rh-hideout/pokeemerald-expansion/pull/3454)). 1.8.0 "Added defines to RHH's rom header: `MOVES_COUNT` and `NUM_SPECIES` ... `ITEMS_COUNT` and `ITEM_NAME_LENGTH`" ([1.8.0 changelog](https://github.com/rh-hideout/pokeemerald-expansion/blob/master/docs/changelogs/1.8.x/1.8.0.md), line 212). The count fields were not backported: the commit that adds them is not an ancestor of the 1.7.1 to 1.7.4 tags (GitHub compare API).
- Nothing in the struct gives a RAM address, a table stride, a field offset or a trainer count.

### 1.2 Where it sits

- The cartridge header file `src/rom_header.s` is exactly 0x100 bytes (0xC0 header bytes, 0x0C bytes of word and GPIO fields, 0x34 spare) ([rom_header.s](https://github.com/rh-hideout/pokeemerald-expansion/blob/master/src/rom_header.s)), derived. The GF header follows at 0x08000100; a third-party tool hard-codes the same address ([Rogue Assistant `GameData.h`](https://github.com/Pokabbie/pokeemerald-rogue-assistant/blob/main/RogueAssistantCpp/Inc/GameData.h): `c_GFHeaderAddress = c_RomAddress + 0x100`).
- Linker order is cartridge header, GF header, RHH header, `crt0`: [1.7.0](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.7.0/ld_script_modern.ld), [1.12.3](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.12.3/ld_script_modern.ld) (`src/rom_header_gf.o(.text.*); src/rom_header_rhh.o(.text.*)`), [1.13.0](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.13.0/ld_script_modern.ld) and [master](https://github.com/rh-hideout/pokeemerald-expansion/blob/master/ld_script_modern.ld) (`KEEP(*.o(.text.header_gf)); KEEP(*.o(.text.header_rhh));`).
- `struct GFRomHeader` is 0x104 bytes in all 64 tags from 1.3.0 to 1.17.2 and master, with identical offsets in the 63 tags from 1.4.0 (host-compiled from each tag's [`src/rom_header_gf.c`](https://github.com/rh-hideout/pokeemerald-expansion/blob/master/src/rom_header_gf.c)), derived. If the RHH block directly follows, that puts it at 0x08000204. Tags 0.9.0 to 1.2.0 have a single `seenOffset` instead of `seen1Offset`/`seen2Offset`, so their header is 0x100 bytes and every field after 0x5C sits 4 bytes earlier (`abilityNames` 0xBC, `items` 0xC4, `moves` 0xC8); that is before the RHH header exists.
- Not matching that: pokedaisy's notes for Emerald Imperium (expansion 1.10.0) say the block is at 0x080001FC ([`gen_expansion_tables.py`](https://github.com/lidor30/pokedaisy/blob/main/scripts/gen_expansion_tables.py) line 197), and BananaLinux's header comment says "at 0x200" ([`expansion.h`](https://github.com/JorreFog/BananaLinux/blob/main/ui/src/gba/expansion.h)). Neither number was checked by me. Both tools scan for the magic instead of using a fixed offset: pokedaisy `data.find(b"RHHEXP", 0, 0x400)` ([`rom_identify.py`](https://github.com/lidor30/pokedaisy/blob/main/scripts/rom_identify.py) line 218), BananaLinux scans 0x100 to 0x400 in steps of 2 ([`expansion.cpp`](https://github.com/JorreFog/BananaLinux/blob/main/ui/src/gba/expansion.cpp)).
- In 1.7.0 and 1.7.1 the struct has no section attribute ([1.7.0 file](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.7.0/src/rom_header_rhh.c)), so it is an ordinary `.rodata` constant that the `.text.*` rule does not catch, inferred. [PR 3980](https://github.com/rh-hideout/pokeemerald-expansion/pull/3980) ("RHH rom header was not in the correct section") fixed this for 1.7.2.

### 1.3 Presence and meaning of the version

- `static const` with no `USED` until [PR 7187](https://github.com/rh-hideout/pokeemerald-expansion/pull/7187) ("force RHH Rom Header to always be present", merged 2025-06-23, first in 1.12.1). [PR 7261](https://github.com/rh-hideout/pokeemerald-expansion/pull/7261): "`--gc-sections` removes unused headers/version identifiers even with `USED`. This PR keeps them even with this flag enabled" (merged 2025-07-02, first in 1.13.0; not in 1.12.1 to 1.12.3). The Makefile passes `--gc-sections` in both link branches ([Makefile](https://github.com/rh-hideout/pokeemerald-expansion/blob/master/Makefile) lines 569 and 577). Release tags containing each commit were found with the GitHub compare API.
- A reported expansion hack without the block: Dreamstone Mysteries (version only from its debug menu, "v1.11.2 Development Build"), per [pokedaisy's notes](https://github.com/lidor30/pokedaisy/blob/main/scripts/gen_expansion_tables.py) (line 276). Third-party, unverified.
- The version comes from [`include/constants/expansion.h`](https://github.com/rh-hideout/pokeemerald-expansion/blob/master/include/constants/expansion.h): master reads 1.17.3 with `EXPANSION_TAGGED_RELEASE FALSE`; [`upcoming`](https://github.com/rh-hideout/pokeemerald-expansion/blob/upcoming/include/constants/expansion.h) reads 1.18.0, also FALSE. The release procedure raises the patch number and sets the flag to FALSE right after tagging ([`expansion_versions.md`](https://github.com/rh-hideout/pokeemerald-expansion/blob/master/docs/team_procedures/expansion_versions.md), step 6). So an untagged snapshot reports the next patch number with flag bit 0 clear. Example: Heart and Soul 2.0.6 has `Last version: 1.15.1`, patch 2, `TAGGED_RELEASE FALSE` ([expansion.h](https://github.com/PokemonHnS-Development/pokehns-expansion/blob/Release-v2.0.6/include/constants/expansion.h)). Rogue's expansion branch reads 1.7.4 with `TAGGED_RELEASE TRUE` ([expansion.h](https://github.com/Pokabbie/pokeemerald-rogue/blob/expansion/include/constants/expansion.h)).

### 1.4 Game code and title

- Defaults: `GAME_VERSION ?= EMERALD`, `TITLE ?= POKEMON EMER`, `GAME_CODE ?= BPEE`, `MAKER_CODE := 01`, `REVISION := 0`, written by `gbafix` ([Makefile](https://github.com/rh-hideout/pokeemerald-expansion/blob/master/Makefile) lines 1-4, 24-25, 574; [INSTALL.md](https://github.com/rh-hideout/pokeemerald-expansion/blob/master/INSTALL.md) shows `gbafix ... -t"POKEMON EMER" -cBPEE -m01 -r0`). A default build therefore writes the same title and game code as retail Emerald (retail strings not re-checked here), so the cartridge header alone does not separate the two; pokedaisy uses "same-offset likeness to the retail ROM" plus the RHHEXP block for that ([rom_identify.py](https://github.com/lidor30/pokedaisy/blob/main/scripts/rom_identify.py), module docstring).
- Since 1.14.0 the Makefile also builds FireRed and LeafGreen: `make firered` gives `POKEMON FIRE` / `BPRE`, `make leafgreen` gives `POKEMON LEAF` / `BPGE`. `firered` appears in the Makefile at 1.14.0 and not at 1.13.0 ([1.14.0 Makefile](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.14.0/Makefile)).
- Hacks can change the code: a third-party note lists Monomyth with code `MONE` ([pokedaisy CLAUDE.md](https://github.com/lidor30/pokedaisy/blob/main/CLAUDE.md)); unverified.

### 1.5 What the GF header adds

Same file ([`src/rom_header_gf.c`](https://github.com/rh-hideout/pokeemerald-expansion/blob/master/src/rom_header_gf.c)). Offsets from the struct start (ROM address = 0x08000100 + offset), derived; identical in the 63 tags from 1.4.0 to 1.17.2 and master (the `speciesInfo` field is named `baseStats` through 1.3.0).

| Field | Offset | Notes |
|---|---|---|
| `version`, `language`, `gameName[32]` | 0x00, 0x04, 0x08 | `gameName` = "pokemon emerald version" |
| `monSpeciesNames`, `moveNames` | 0x44, 0x48 | assignments commented out ("Handled in gSpeciesInfo" from 1.7.0, "Handled in gMovesInfo" from 1.8.0), so NULL in those builds |
| `flagsOffset`, `varsOffset`, `pokedexOffset`, `seen1Offset` | 0x50, 0x54, 0x58, 0x5C | `offsetof` into SaveBlock1/2 |
| `playerNameLength`, `trainerNameLength`, `pokemonNameLength1/2` | 0x74 to 0x77 | `POKEMON_NAME_LENGTH` |
| `saveBlock2Size`, `saveBlock1Size` | 0x88, 0x8C | `sizeof` |
| `partyCountOffset`, `partyOffset` | 0x90, 0x94 | inside SaveBlock1 |
| `trainerIdOffset`, `playerNameOffset`, `playerGenderOffset` | 0x9C, 0xA0, 0xA4 | inside SaveBlock2 |
| `speciesInfo` | 0xBC | pointer to `gSpeciesInfo` |
| `abilityNames`, `abilityDescriptions` | 0xC0, 0xC4 | commented out from 1.8.0 ("handled in gAbilitiesInfo") |
| `items`, `moves` | 0xC8, 0xCC | `gItemsInfo`, `gMovesInfo` (from 1.8.0; `gItems` and `gBattleMoves` before) |
| `gcnLinkFlagsOffset`, `gameClearFlag`, `ribbonFlag` | 0xD8, 0xDC, 0xE0 | flag IDs |
| `bagCountItems` ... `bagCountBerries`, `pcItemsCount` | 0xE4 to 0xE9 | bag pocket capacities as bytes |
| `pcItemsOffset`, `giftRibbonsOffset` | 0xEC, 0xF0 | |
| `enigmaBerryOffset`, `enigmaBerrySize` | 0xF4, 0xF8 | only set when `FREE_ENIGMA_BERRY == FALSE` |

The header lists no RAM address and no bag-pocket offset. The header pointer history across tags: all name tables live behind header pointers through 1.6.x; 1.7.0 drops the species-name pointer; 1.8.0 drops the move-name and ability pointers (checked in [1.7.0](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.7.0/src/rom_header_gf.c) and [1.8.0](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.8.0/src/rom_header_gf.c)).

## 2. Pokémon struct layout

Source: [`include/pokemon.h` at 1.17.2](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.17.2/include/pokemon.h) lines 132-299 (identical at master); vanilla: [pret `include/pokemon.h`](https://github.com/pret/pokeemerald/blob/master/include/pokemon.h).

### 2.1 What did not change

- Sizes: `struct BoxPokemon` 80 bytes, `struct Pokemon` 100 bytes (status @80, level @84, mail @85, hp @86, maxHP @88, then attack, defense, speed, spAttack, spDefense to @98). `NUM_SUBSTRUCT_BYTES` is the max of the four substructs, "By default they are all 12 bytes." Static asserts on the layout (compiled with clang for ARM): `sizeof(BoxPokemon) == 80`, `sizeof(Pokemon) == 100`; derived.
- Encryption: each of the 12 u32 words in `secure` is XORed with `otId` then `personality` ([`EncryptBoxMon` / `DecryptBoxMon`](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.17.2/src/pokemon.c#L1892-L1908)).
- Substruct order: `sSubstructOffsets[4][24]` indexed by `personality % 24` ([line 1910](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.17.2/src/pokemon.c#L1910)). I converted the table to order strings: it equals the canonical GAEM, GAME, GEAM, GEMA, GMAE, GMEA, AGEM, AGME, AEGM, AEMG, AMGE, AMEG, EGAM, EGMA, EAGM, EAMG, EMGA, EMAG, MGAE, MGEA, MAGE, MAEG, MEGA, MEAG (growth, attacks, EVs/condition, misc).
- Checksum: sum of `raw[i] + (raw[i] >> 16)` over the 12 decrypted words, truncated to u16 ([`CalculateBoxMonChecksum`](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.17.2/src/pokemon.c#L1339-L1347)); that is the sum of the 24 halfwords, same as vanilla.
- Substruct 2 (EVs, contest stats) is byte-for-byte vanilla.

### 2.2 Bit layout since 1.9.0 (1.8.0 differs only where marked)

Positions are within the decrypted 12-byte substruct, little-endian, low bit first. Cross-checked with `clang --target=arm-none-eabi -fdump-record-layouts` on the struct text (derived). pokedaisy applies `speciesMask 0x07FF`, `moveMask 0x07FF` and `ppMask 0x7F` to Emerald Imperium (expansion 1.10.0) ([imperium.toml](https://github.com/lidor30/pokedaisy/blob/main/gamedata/gen3/hacks/imperium.toml)) and reports that Heart and Soul's `BoxPokemon` "packs species:11|teraType:5" (raw 22683 reads as 155) ([heart_and_soul.toml](https://github.com/lidor30/pokedaisy/blob/main/gamedata/gen3/hacks/heart_and_soul.toml)); third-party measurements on real ROMs.

| Where | Vanilla Emerald | Expansion |
|---|---|---|
| Sub0 u16 @0 | `species` (16 bits) | `species` bits 0-10, `teraType` bits 11-15 |
| Sub0 u16 @2 | `heldItem` (16 bits) | `heldItem` bits 0-9 (max 1023) |
| Sub0 u32 @4 | `experience` (32 bits) | `experience` bits 0-20 (max ~2.09 million), `nickname11` bits 21-28 |
| Sub0 u16 @10 | `filler` | `pokeball` bits 0-5, `nickname12` bits 6-13 |
| Sub1 u16 @0,2,4,6 | `moves[4]` (16 bits each) | `move1..4` bits 0-10; bits 11-15 of the first two words are `evolutionTracker1/2` (the second is 4 bits in 1.8.x, 5 from 1.9.0); bits 14 and 15 of the fourth word are hyper training HP and ATK |
| Sub1 bytes @8-11 | `pp[4]` (8 bits each) | `pp1..4` bits 0-6; bit 7 of each is hyper training DEF, SPE, SPA, SPD |
| Sub3 u16 @2 | metLevel 0-6, metGame 7-10, `pokeball` 11-14, otGender 15 | metLevel 0-6, metGame 7-10, `dynamaxLevel` 11-14, otGender 15 |
| Sub3 u32 @4 | IVs bits 0-29, `isEgg` 30, `abilityNum` 31 | IVs bits 0-29, `isEgg` 30, `gigantamaxFactor` 31 |
| Sub3 u32 @8 | ribbons bits 0-26, unused 27-30, fateful 31 | ribbons bits 0-26, `isShadow` 27, unused 28, `abilityNum` bits 29-30 (2 bits), fateful 31 |

### 2.4 How derived values are computed

- Shiny: `((HIHALF(otId) ^ LOHALF(otId) ^ HIHALF(personality) ^ LOHALF(personality)) < SHINY_ODDS) ^ shinyModifier`, with `SHINY_ODDS 8` ([`MON_DATA_IS_SHINY`](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.17.2/src/pokemon.c#L2480-L2484), [`GET_SHINY_VALUE`](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.17.2/include/pokemon.h#L717), [`SHINY_ODDS`](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.17.2/include/constants/pokemon.h#L107)). Before 1.8.0 there is no modifier bit. `SHINY_ODDS 8` and `GET_SHINY_VALUE` are the same in [pret](https://github.com/pret/pokeemerald/blob/master/include/constants/pokemon.h#L94).
- Nature: `GetNatureFromPersonality` is `personality % 25`. The effective nature (mints) is `(personality % 25) ^ hiddenNatureModifier` ([`MON_DATA_HIDDEN_NATURE`](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.17.2/src/pokemon.c#L2486-L2490)); the stat calculation reads the effective nature ([line 1389](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.17.2/src/pokemon.c#L1389)). `NATURE_*` IDs are 0-24 as in [pret](https://github.com/pret/pokeemerald/blob/master/include/constants/pokemon.h#L47-L72).
- Ability: `abilityNum` (2 bits: 0 and 1 normal, 2 hidden) indexes `gSpeciesInfo[species].abilities[3]`; an empty slot falls back to the other hidden slots, then to the first non-empty slot ([`GetAbilityBySpecies`](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.17.2/src/pokemon.c#L3080-L3103); `NUM_NORMAL_ABILITY_SLOTS 2`, `NUM_ABILITY_SLOTS 3` in [`constants/pokemon.h`](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.17.2/include/constants/pokemon.h#L415-L417)).
- Gender: `genderRatio` of 0x00, 0xFE, 0xFF mean male, female, genderless; otherwise female if `genderRatio > (personality & 0xFF)` ([`GetBoxMonGender`](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.17.2/src/pokemon.c#L1786-L1803)). Same rule as vanilla.
- Level of a boxed mon: walk `gExperienceTables[growthRate][level]` up to `MAX_LEVEL 100` ([`GetLevelFromBoxMonExp`](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.17.2/src/pokemon.c#L1486)). `STATIC_ASSERT(MAX_LEVEL <= 100, ...)` guards the 21-bit experience field ([pokemon.c line 770](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.17.2/src/pokemon.c#L770)).
- HP and status of a boxed mon (1.8.0 on): `hpLost` and a 4-bit index into `sCompressedStatuses` (none, sleep 1-5, poison, burn, freeze, paralysis, toxic, frostbite); current HP is `maxHP - hpLost` after `CalculateMonStats` ([`BoxMonToMon`](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.17.2/src/pokemon.c#L1459-L1472), [`sCompressedStatuses`](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.17.2/src/pokemon.c#L689-L703)). Vanilla boxes drop both.
- Hidden Power: the six IV low bits form a 0-63 value; type = `((count - 1) * bits) / 63` over the types with `isHiddenPowerType` in `gTypesInfo` ([`battle_main.c`](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.17.2/src/battle_main.c)). The flag exists from 1.11.0 (absent in `src/data/types_info.h` at 1.9.0 and 1.10.x, present at 1.11.0). At 1.17.2 sixteen types are flagged ([types_info.h](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.17.2/src/data/types_info.h)): Fighting through Dark except Normal, Mystery, Fairy and Stellar, which is the vanilla Gen 3 list.

### 2.5 Config flags and hack divergence

- No `#if` appears inside `BoxPokemon` or the four substructs. The only config-dependent size terms are `POKEMON_NAME_LENGTH` (`nickname` is `min(10, ...)`, so a value below 10 shrinks the field) and `PLAYER_NAME_LENGTH`.
- The source tells hack authors to widen fields when constants outgrow them: "Increase the number of bits both on the struct AND in the corresponding assert. This will likely break user's saves ..." with the example `heldItem:10` to `heldItem:11` ([pokemon.c lines 705-727](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.17.2/src/pokemon.c#L705-L727)), and a compile-time check `sBoxPokemonConstantsFit` ([line 729](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.17.2/src/pokemon.c#L729)). A hack on a given tag can therefore carry different widths.
- Observed divergence in public source:
  - Rogue's `expansion` branch (expansion 1.7.4, which has the vanilla-shaped mon): `species:11`, `heldItem1:10` + `heldItem2:1`, `teraType:5`, `experience:21`, `u16 moves[4]`, `isShiny:3`, `genderFlag:3`, `tutorMoveLvl:2`, `abilityNum:2` ([pokemon.h](https://github.com/Pokabbie/pokeemerald-rogue/blob/expansion/include/pokemon.h)). pokedaisy adds that its `struct Pokemon` is 104 bytes ([emerald_rogue.toml](https://github.com/lidor30/pokedaisy/blob/main/gamedata/gen3/hacks/emerald_rogue.toml), third-party).
  - Inclement Emerald: `nature:5` in Sub3, `pokeball:5` and `abilityNum:2` in the third Sub3 word, `metGame:3` ([pokemon.h](https://github.com/BuffelSaft/pokeemerald/blob/master/include/pokemon.h)).
  - Elite Redux: no substructs, no encryption, `species:16`, `move1:11` packed with `experience:21`, `isShiny:2`, `abilityNum:2`, `struct Pokemon` adds `pp[4]` ([pokemon.h](https://github.com/Elite-Redux/eliteredux-source/blob/upcoming/include/pokemon.h)). Summing the declared fields gives 76 bytes (derived); pokedaisy reports 0x4C ([elite_redux.toml](https://github.com/lidor30/pokedaisy/blob/main/gamedata/gen3/hacks/elite_redux.toml)).
  - SoulGold keeps mons unencrypted in 96 bytes and Heart and Soul moved the save position (BananaLinux [header comment](https://github.com/JorreFog/BananaLinux/blob/main/ui/src/gba/expansion.h), third-party).

## 3. Species, move, item and ability data

### 3.1 IDs and counts

- Species IDs follow national dex order for base species at every tag: `SPECIES_BULBASAUR 1` ... `SPECIES_CELEBI 251`, `SPECIES_TREECKO 252`, `SPECIES_DEOXYS_NORMAL 386`, `SPECIES_TURTWIG 387` ([master species.h](https://github.com/rh-hideout/pokeemerald-expansion/blob/master/include/constants/species.h)). Vanilla uses internal order: `SPECIES_OLD_UNOWN_B` 252 to `SPECIES_OLD_UNOWN_Z` 276, `SPECIES_TREECKO 277`, `NUM_SPECIES` 412 ([pret species.h](https://github.com/pret/pokeemerald/blob/master/include/constants/species.h)). Forms, Mega Evolutions and later species are appended after the national range; `SPECIES_EGG = NUM_SPECIES`; the enum has no `#if` ([master](https://github.com/rh-hideout/pokeemerald-expansion/blob/master/include/constants/species.h)).
- `NUM_SPECIES` per tag (compiled from each tag's `species.h`): 1234 (1.0.0-1.4.3), 1235 (1.5.0-1.6.2), 1523 (1.7.0), 1524 (1.8.0-1.12.x), 1550 (1.14.0), 1573 (1.15.0-1.17.2). The 11-bit mon field allows IDs up to 2047.
- `MOVES_COUNT`: 779 (1.0.0), 848 (1.7.0 to 1.17.2). `ABILITIES_COUNT`: 268 (1.0.0), 311 (1.7.0-1.15.x), 320 (1.17.2). `ITEMS_COUNT`: 758 (1.0.0), 816 (1.7.0), 828 (1.8.0), 829 (1.10.0-1.12.0), 855 (1.14.0); the 1.15+ `items.h` uses preprocessor-generated TM entries and I did not compute it. The held-item field caps `ITEMS_COUNT` at 1023.
- `species_enabled.h` has about 540 lines defining `P_FAMILY_*` toggles plus `P_GEN_n_POKEMON` switches; it controls which entries get data, not the enum values. Its header warns that changing the latest enabled generation "WILL change the saveblock due to Dex flags" ([species_enabled.h](https://github.com/rh-hideout/pokeemerald-expansion/blob/master/include/config/species_enabled.h)).

### 3.2 `struct SpeciesInfo`

[1.17.2](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.17.2/include/pokemon.h#L394-L527). The header comment `/*0xC4*/` is a hand-kept note, not a size guarantee.

- Before 1.7.0 the struct is the 0x24-byte vanilla-shaped `BaseStats`/`SpeciesInfo` and names sit in separate `gSpeciesNames` ([1.4.0](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.4.0/include/pokemon.h)). From 1.7.0 `speciesName` is inline ("`gSpeciesNames` array -> `speciesName` field", [1.7.0 changelog](https://github.com/rh-hideout/pokeemerald-expansion/blob/master/docs/changelogs/1.7.x/1.7.0.md) line 147).
- Field order up to `natDexNum` is the same at every tag from 1.7.0 to 1.17.2 (grouping of the struct text across tags, ignoring comments and enum annotations), except `forceTeraType` replacing `padding1` at byte 9 in 1.9.0. In order, with offsets from the declared sizes (derived; the stat, type, gender ratio and name offsets match pokedaisy's measurements on Imperium, Wishes of Tomorrow and, by its note, Heart and Soul and Lazarus, [gen_expansion_tables.py](https://github.com/lidor30/pokedaisy/blob/main/scripts/gen_expansion_tables.py) lines 197-262):

| Offset | Field |
|---|---|
| 0x00-0x05 | base HP, Attack, Defense, Speed, Sp.Atk, Sp.Def (u8) |
| 0x06 | `types[2]` (packed enum, u8) |
| 0x08 | `catchRate`; 0x09 `forceTeraType` (1.9.0+) |
| 0x0A | `expYield` (u16); 0x0C EV yield bitfield (u16) |
| 0x0E, 0x10 | `itemCommon`, `itemRare` (u16) |
| 0x12-0x15 | `genderRatio`, `eggCycles`, `friendship`, `growthRate` |
| 0x16 | `eggGroups[2]` |
| 0x18 | `abilities[3]` (packed `enum Ability`, u16 each) |
| 0x1E | `safariZoneFleeRate` |
| 0x1F | `categoryName[13]` |
| 0x2C | `speciesName[POKEMON_NAME_LENGTH + 1]` (11 bytes at 10, 13 at 12) |

- `natDexNum` follows `cryId`; both are `:16` bitfields of non-packed enums (`PokemonCry`, `NationalDexOrder`, `BodyColor`, `EggIds` are not declared packed), so their offsets depend on enum width rules I did not compute. pokedaisy records `natDexNum` at +0x3A for Rogue's 1.7.4-based table ([emerald_rogue.toml](https://github.com/lidor30/pokedaisy/blob/main/gamedata/gen3/hacks/emerald_rogue.toml), third-party).
- Fields after the name block depend on config: `#if P_GENDER_DIFFERENCES` (five female pointers, two female size bytes, `iconPalIndexFemale`), `#if P_FOOTPRINTS` (footprint pointer), `#if OW_POKEMON_OBJECT_EVENTS` with `OW_PKMN_OBJECTS_SHARE_PALETTES` and `P_GENDER_DIFFERENCES` (an `ObjectEventGraphicsInfo` plus palette pointers). `EGG_GROUPS_PER_MON` (2), `NUM_ABILITY_SLOTS` (3) and `POKEMON_NAME_LENGTH` (10 at 1.8.0, 12 from 1.10.0) are constants a hack could change. So stride (`sizeof`) varies with config and version. Third-party measurements of the stride: 0x104 (Imperium on 1.10.0; Wishes of Tomorrow on 1.15.3), 0xA8 (Team Rocket Edition 2026 on 1.14.4), 0x98 (Rogue 2.2.1-EX, [emerald_rogue.toml](https://github.com/lidor30/pokedaisy/blob/main/gamedata/gen3/hacks/emerald_rogue.toml)), and 0x10C, 0xD0, 0xD4, 0x118, 0x120 for other hacks in the same script ([gen_expansion_tables.py](https://github.com/lidor30/pokedaisy/blob/main/scripts/gen_expansion_tables.py) lines 65-300). The RHH header's `numSpecies` plus `gSpeciesInfo`'s size would give the stride; no header carries the size.
- Type IDs: `TYPE_NONE 255` and `TYPE_NORMAL 0` through 1.8.x; `TYPE_NONE 0`, `TYPE_NORMAL 1`, `TYPE_MYSTERY 10`, `TYPE_FIRE 11`, `TYPE_FAIRY 19`, `TYPE_STELLAR 20` from 1.9.0 ([1.8.0](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.8.0/include/constants/pokemon.h) vs [1.9.0](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.9.0/include/constants/pokemon.h)). The 1.9.0 changelog lists "Type Info refactors" ([PR 4462](https://github.com/rh-hideout/pokeemerald-expansion/pull/4462), [1.9.0 changelog](https://github.com/rh-hideout/pokeemerald-expansion/blob/master/docs/changelogs/1.9.x/1.9.0.md) line 211) but does not state the renumbering.
- Growth rate IDs equal vanilla's 0-5: `GROWTH_MEDIUM_FAST, ERRATIC, FLUCTUATING, MEDIUM_SLOW, FAST, SLOW` ([expansion](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.17.2/include/constants/pokemon.h#L245-L252), [pret](https://github.com/pret/pokeemerald/blob/master/include/constants/pokemon.h#L219-L224)).

### 3.3 Moves, items, abilities

- Moves: through 1.7.x `struct BattleMove` holds no name; names are in a `gMoveNames` array behind the GF `moveNames` pointer. From 1.8.0 (`gBattleMoves` renamed `gMovesInfo`, "Moved move names to `gMovesInfo`", [1.8.0 changelog](https://github.com/rh-hideout/pokeemerald-expansion/blob/master/docs/changelogs/1.8.x/1.8.0.md) lines 45-50, [PR 3999](https://github.com/rh-hideout/pokeemerald-expansion/pull/3999)) `struct MoveInfo` starts with `const u8 *name`, then `const u8 *description`. `MOVE_NAME_LENGTH` is `((B_EXPANDED_MOVE_NAMES == TRUE) ? 16 : 12)` at 1.8.0 and `16` from 1.10.0. Strides measured by pokedaisy: 0x34 (1.10.0), 0x30 (1.11.2), 0x3C (1.14.4), 0x44 (1.15.3). Move field in a mon is 11 bits.
- Items: `struct Item` has `u8 name[ITEM_NAME_LENGTH]` inline at +0x14 (after `price` u32, `secondaryId` u16, `fieldUseFunc`, `description`, `effect`) through 1.12.x; from 1.13.0 `name` is `const u8 *name` at the same offset with `pluralName` after it ([1.12.0](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.12.0/include/item.h) vs [1.13.0](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.13.0/include/item.h)); the struct is `ItemInfo` from 1.15.0 ([master item.h](https://github.com/rh-hideout/pokeemerald-expansion/blob/master/include/item.h)). `ITEM_NAME_LENGTH` is 14 at 1.8.0 and 20 from 1.10.0 (it is in the RHH header). Strides measured by pokedaisy: 0x2C, 0x50, 0x54 ([gen_expansion_tables.py](https://github.com/lidor30/pokedaisy/blob/main/scripts/gen_expansion_tables.py)); the 0x50 entries have the name inline.
- Abilities: `struct Ability` (1.8.0-1.13.x) then `struct AbilityInfo` (1.14.0+) with the same members: `u8 name[ABILITY_NAME_LENGTH + 1]`, `const u8 *description`, `s8 aiRating`, one flag byte ([master](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.17.2/include/pokemon.h#L567-L578)). `ABILITY_NAME_LENGTH` is 12 or 16 by `B_EXPANDED_ABILITY_NAMES` at 1.8.0 and 16 from 1.10.0 ([constants/global.h](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.17.2/include/constants/global.h#L170)). pokedaisy records `gAbilitiesInfo` as 0x1C-byte records read through the RHHEXP pointer, for ROMs it lists as expansion 1.9.2 to 1.15.2 ([ported.toml](https://github.com/lidor30/pokedaisy/blob/main/gamedata/gen3/records/ported.toml) lines 1148 and 3481; third-party). The RHH header points to `gAbilitiesInfo` (section 1.1); no GF header field does after 1.8.0.
- Name lengths in vanilla for contrast: item 14, Pokémon 10, move 12, ability 12 ([pret constants/global.h](https://github.com/pret/pokeemerald/blob/master/include/constants/global.h)). Master: 20, 12, 16, 16.

## 4. Build outputs

- `make` produces `pokeemerald.elf` and `pokeemerald.map` by default: `ELF := $(ROM:.gba=.elf)`, `MAP := $(ROM:.gba=.map)`, linker `-Map` in both link branches; the ROM is `$(OBJCOPY) -O binary` of the ELF followed by `gbafix` ([Makefile](https://github.com/rh-hideout/pokeemerald-expansion/blob/master/Makefile) lines 127-129, 565-590). The `.gba` therefore holds no symbol table. `.elf`, `.map` and `.sym` are in [`.gitignore`](https://github.com/rh-hideout/pokeemerald-expansion/blob/master/.gitignore).
- `make syms` writes `pokeemerald.sym` through `objdump -t | sort -u | grep -E "^0[2389]" | perl ...` ([Makefile](https://github.com/rh-hideout/pokeemerald-expansion/blob/master/Makefile) lines 592-594). The `syms` rule, `DINFO` and the linker `-Map` option are present in the Makefile of all 69 tags (0.9.0 to 1.17.2).
- DWARF is not on by default: `-O2` without `-g`. `-g` is added by `DINFO=1` or `DEBUG=1`; INSTALL.md: "To build pokeemerald.elf with debug symbols ... `make debug`" ([INSTALL.md](https://github.com/rh-hideout/pokeemerald-expansion/blob/master/INSTALL.md), "Building with debug info"; Makefile lines 197-203). `make release` enables LTO by default (`USE_LTO_ON_RELEASE ?= 1`, [config.mk](https://github.com/rh-hideout/pokeemerald-expansion/blob/master/config.mk)) and defines `RELEASE`, which `include/config/general.h` turns into `NDEBUG` ([general.h](https://github.com/rh-hideout/pokeemerald-expansion/blob/master/include/config/general.h)), so a release build is a different binary from a plain build.
- Publishing: expansion's CI workflow has no step that uploads `.sym` or `.map` ([build.yml](https://github.com/rh-hideout/pokeemerald-expansion/blob/master/.github/workflows/build.yml)); the repo has no `symbols` branch (branches: `master`, `upcoming`, `upcoming-decap`, one contributor branch, [list](https://github.com/rh-hideout/pokeemerald-expansion/branches)). none of the 69 GitHub releases has an uploaded asset ([releases](https://github.com/rh-hideout/pokeemerald-expansion/releases), checked through the releases API). pret does publish: [pret/pokeemerald `symbols` branch](https://github.com/pret/pokeemerald/tree/symbols) holds `pokeemerald.sym`.
- A build of a hack's source tag need not match the released ROM: Heart and Soul's release ROM has most of upper EWRAM 4 bytes lower than a build of its source tag ([heart_and_soul.toml](https://github.com/lidor30/pokedaisy/blob/main/gamedata/gen3/hacks/heart_and_soul.toml), third-party, unverified).
- Existing exporters of struct offsets or RAM addresses from expansion builds: none found in the repo or its docs. The documented practice is outside: pokedaisy compiles `offsetof` against the matching tag's headers and runs `nm` on a reference build ([playbook](https://github.com/lidor30/pokedaisy/blob/main/.claude/skills/add-rom/playbooks/expansion.md), steps 1-2).
- Embedded symbol table: one third-party note says the R.O.W.E. ROM "carries its own symbol table (0x08FB0670)" ([pokedaisy CLAUDE.md](https://github.com/lidor30/pokedaisy/blob/main/CLAUDE.md), unverified); R.O.W.E. is not an expansion build per the same note.

## 6. Save block, bag, player

Source: [`include/global.h` at 1.17.2](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.17.2/include/global.h) (`SaveBlock1` line 1095, `SaveBlock2` line 588, `Bag` line 1086, `ItemSlot` line 676), [`include/config/save.h`](https://github.com/rh-hideout/pokeemerald-expansion/blob/master/include/config/save.h).

- Early SaveBlock1 offsets are the vanilla ones and sit before every conditional field: `playerPartyCount` 0x234, `playerParty` 0x238, `money` 0x490, `coins` 0x494, `registeredItem` 0x496, `pcItems[50]` 0x498, `bag` 0x560 (0x2E8 bytes, ends 0x848), `pokeblocks` 0x848 (struct comments; the lines before the first `#if` are unchanged across all tags diffed).
- SaveBlock2 start is vanilla: `playerName[8]` 0x00, `playerGender` 0x08, `playerTrainerId[4]` 0x0A, play time 0x0E to 0x12.
- `FREE_*` flags (new in 1.8.0 from the "Saveblock Cleansing" branch, [1.8.0 changelog](https://github.com/rh-hideout/pokeemerald-expansion/blob/master/docs/changelogs/1.8.x/1.8.0.md) lines 315-321) remove fields with `#if FREE_x == FALSE`. In SaveBlock1 the first conditional is `FREE_EXTRA_SEEN_FLAGS_SAVEBLOCK1` (`filler1[0x34]` at 0x988, after the bag), so removing fields shifts `flags`, `vars`, `objectEvents`, `dexSeen/dexCaught` and later data, not the party, money or bag. In SaveBlock2 `FREE_EXTRA_SEEN_FLAGS_SAVEBLOCK2` shrinks `struct Pokedex` by 0x68 bytes and so shifts `localTimeOffset`, `gcnLinkFlags` and `encryptionKey` (0xAC in vanilla). Defaults are all FALSE, which keeps the vanilla layout.
- Money and bag quantities are XORed with `gSaveBlock2Ptr->encryptionKey` ([`money.c` lines 71 and 76](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.17.2/src/money.c#L71)); the GF header has no offset for the key, but `gcnLinkFlagsOffset` is the field before it in the struct (`gcnLinkFlags` at +0xA8, `encryptionKey` at +0xAC in vanilla), a source-order inference. Measured by third parties: key at SaveBlock2+0x44 in Imperium (0xAC - 0x68, consistent with `FREE_EXTRA_SEEN_FLAGS_SAVEBLOCK2 == TRUE`), +0xAC in Heart and Soul, +0x4C in Rogue ([imperium.toml](https://github.com/lidor30/pokedaisy/blob/main/gamedata/gen3/hacks/imperium.toml), [heart_and_soul.toml](https://github.com/lidor30/pokedaisy/blob/main/gamedata/gen3/hacks/heart_and_soul.toml), [emerald_rogue.toml](https://github.com/lidor30/pokedaisy/blob/main/gamedata/gen3/hacks/emerald_rogue.toml)).
- Bag: item slot is `{ enum Item itemId; u16 quantity; }` (packed enum, so 4 bytes). Pocket capacities are `#define`s: `BAG_ITEMS_COUNT 30`, `BAG_KEYITEMS_COUNT 30`, `BAG_POKEBALLS_COUNT 16`, `BAG_TMHM_COUNT 64`, `BAG_BERRIES_COUNT 46`, `PC_ITEMS_COUNT 50` ([constants/global.h](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.17.2/include/constants/global.h#L99-L117)), equal to vanilla. The GF header exports these as bytes (section 1.5). Since 1.13.0 the five arrays are wrapped in `struct Bag` with the same offsets ([1.13.0 changelog](https://github.com/rh-hideout/pokeemerald-expansion/blob/master/docs/changelogs/1.13.x/1.13.0.md) "Bag refactor", line 20). The upstream `enum Pocket` has five pockets ([constants/item.h](https://github.com/rh-hideout/pokeemerald-expansion/blob/master/include/constants/item.h)); hacks add pockets (Imperium 6, Team Rocket Edition 8 per pokedaisy), tracked in a runtime `gBagPockets` table.
- Held item in a mon is 10 bits; an item ID in the bag slot is 16 bits.
- Badges and system flags: `FLAG_BADGE01_GET (SYSTEM_FLAGS + 0x7)`, `FLAG_SYS_GAME_CLEAR (SYSTEM_FLAGS + 0x4)`, `SYSTEM_FLAGS (TRAINER_FLAGS_END + 1) // 0x860` in both expansion and pret ([expansion flags.h](https://github.com/rh-hideout/pokeemerald-expansion/blob/master/include/constants/flags.h) lines 1348-1366). Adding trainers moves them; the GF header's `gameClearFlag` gives the base (BananaLinux uses "game clear + 3" for badge 1, [expansion.h](https://github.com/JorreFog/BananaLinux/blob/main/ui/src/gba/expansion.h)); Wishes of Tomorrow has 896 trainer flags and `FLAG_SYS_POKEMON_GET` 0x880 (third-party).
- `SaveBlock3` is new in 1.8.0 ("Save-compatible SaveBlock3, with 1624 bytes", [1.8.0 changelog](https://github.com/rh-hideout/pokeemerald-expansion/blob/master/docs/changelogs/1.8.x/1.8.0.md) line 267); members depend on config (`OW_USE_FAKE_RTC`, follower NPC, DexNav).
- SaveBlock addresses are not fixed: `gSaveBlock1Ptr` and `gSaveBlock2Ptr` are IWRAM pointers whose targets move between loads (third-party observations of "their targets drift": [emerald_rogue.toml](https://github.com/lidor30/pokedaisy/blob/main/gamedata/gen3/hacks/emerald_rogue.toml), [heart_and_soul.toml](https://github.com/lidor30/pokedaisy/blob/main/gamedata/gen3/hacks/heart_and_soul.toml)). The pointers' own addresses come from the build; no ROM header carries them.

## 7. Battle state

- `gBattleTypeFlags` is still a u32; `gBattleOutcome` a u8 with the same `B_OUTCOME_*` values (1 won ... 10 mon teleported, `1<<7` link ran) ([constants/battle.h](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.17.2/include/constants/battle.h#L101-L166) vs [pret](https://github.com/pret/pokeemerald/blob/master/include/constants/battle.h)). Bit changes in `BATTLE_TYPE_*`, from a grep of `constants/battle.h` at each tag: in 1.8.0 bit 12 `KYOGRE_GROUDON` became `RAID`, bit 14 `REGI` became `14`, and bits 28-30 `GROUDON/KYOGRE/RAYQUAZA` shrank to `30`; in 1.15.0 bit 9 `WALLY_TUTORIAL` became `CATCH_TUTORIAL` and bits 28-29 became `GHOST` and `POKEDUDE`. Bits 0-8, 10-11, 13, 15-27 and 31 are unchanged, including `DOUBLE` (bit 0) and `TRAINER` (bit 3).
- `gBattleWeather` is u16, but the encoding changed. Through 1.10.x it keeps vanilla's `B_WEATHER_RAIN_TEMPORARY`/`PERMANENT` bit pairs; from 1.11.0 it is one bit per `enum BattleWeather` value (`B_WEATHER_RAIN_NORMAL (1 << BATTLE_WEATHER_RAIN)`, plus primal, downpour, sun, sandstorm, hail, snow, fog, strong winds) ([1.17.2](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.17.2/include/constants/battle.h#L476-L511); tag-by-tag grep for `enum BattleWeather` and `B_WEATHER_RAIN_TEMPORARY`).
- Terrain does not exist in vanilla. Through 1.16.x it is `STATUS_FIELD_*_TERRAIN` bits in `u32 gFieldStatuses`; from 1.17.0 it is `enum BattleTerrain` (`B_TERRAIN_GRASSY` ...) in the field timer struct, and `gFieldStatuses` keeps rooms, sports, gravity ([constants/battle.h](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.17.2/include/constants/battle.h#L428-L446), grep per tag).
- `gSideStatuses` is `u32[2]` (vanilla `u16[2]`); side flags are `SIDE_STATUS_REFLECT` (bit 0) ... `SIDE_STATUS_SWAMP` (bit 10) ([battle.h](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.17.2/include/battle.h#L1059), [constants](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.17.2/include/constants/battle.h)). Hazards and screens timers sit in `gSideTimers`.
- `struct BattlePokemon` ([1.17.2](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.17.2/include/pokemon.h#L340-L376)) differs from vanilla: `ability` is its own field, `types[3]`, `statStages[NUM_BATTLE_STATS]`, `moves[4]` as enum, `volatiles` instead of `status2`, `metLevel:7` + `isShiny:1`, `affectionHearts`. Layout events by tag grouping: `metLevel` added 1.4.0; `isShiny` 1.8.0; `type1/type2/type3` to `types[3]` 1.9.1 (same layout); `status2` (4 bytes) replaced by `struct Volatiles` (the 1.13.0 hand comments give 12 bytes) in 1.13.0; `ability` and `types` become enums 1.14.0; `moves` and `item` become enums 1.15.0; `metLevel`/`isShiny` pack into one byte and `affectionHearts` is added in 1.16.0. I did not compute `sizeof(struct BattlePokemon)`.
- Volatiles refactor: "Volatile status refactoring" ([PR 6983](https://github.com/rh-hideout/pokeemerald-expansion/pull/6983)) and "Replaces STATUS2 usage with volatiles ... (but left the old bitfield behind for compatibility with downstream users)" ([PR 7262](https://github.com/rh-hideout/pokeemerald-expansion/pull/7262)) both in [1.13.0](https://github.com/rh-hideout/pokeemerald-expansion/blob/master/docs/changelogs/1.13.x/1.13.0.md) lines 19 and 40-41. The field list is macro-generated (`VOLATILE_DEFINITIONS`) in `constants/battle.h`. My count of fields per tag (a parse with some bit widths unparsed, so counts are exact and bit totals are lower bounds): 50 in 1.13.0-1.13.3, 49 in 1.13.4, 57 in 1.14.0-1.14.1, 58 in 1.14.2-1.14.4, 116 in 1.15.0-1.15.1, 117 in 1.15.2-1.15.3, 120 in 1.16.0-1.16.1, 121 in 1.16.2-1.16.4, 118 in 1.17.0-1.17.2. The field list differs from the previous tag's in 9 of the 21 steps between 1.13.0 and 1.17.2 (1.13.4, 1.14.0, 1.14.2, 1.15.0, 1.15.2, 1.16.0, 1.16.2, 1.17.0, 1.17.2).
- Parties: `gPlayerParty` / `gEnemyParty` / `gPlayerPartyCount` / `gEnemyPartyCount` are replaced by `EWRAM_DATA struct Pokemon gParties[4][6]` and `u8 gPartiesCount[4]` in 1.16.0 (index order `B_TRAINER_PLAYER`, `B_TRAINER_OPPONENT_A`, `B_TRAINER_PARTNER`, `B_TRAINER_OPPONENT_B`) ([1.16.0 changelog](https://github.com/rh-hideout/pokeemerald-expansion/blob/master/docs/changelogs/1.16.x/1.16.0.md) lines 103-120, [constants/battle.h](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.17.2/include/constants/battle.h#L28-L85), [pokemon.c lines 100-109](https://github.com/rh-hideout/pokeemerald-expansion/blob/expansion/1.17.2/src/pokemon.c#L100-L109)). The old names remain as macros over `const` pointer variables defined in ROM (`gPlayerPartyPtr = &gParties[B_TRAINER_PLAYER]`); `gEnemyParty` is marked "Will be removed in 1.17.0" but is still declared at 1.17.2.

## 8. Release cadence and layout churn

- Stated policy: "Minor Release should occur once every three months"; patch releases "AT LEAST once a month"; big-feature freeze 30 days and merge freeze 14 days before a minor; the sample schedule shows major version 2 ([schedule.md](https://github.com/rh-hideout/pokeemerald-expansion/blob/master/docs/team_procedures/schedule.md)).
- Observed (GitHub releases, [list](https://github.com/rh-hideout/pokeemerald-expansion/releases)): 69 tagged releases from 1.0.0 (2022-09-15) to 1.17.2 (2026-10-31). Minor releases: 1.8.0 2024-03-17, 1.9.0 2024-08-02, 1.10.0 2024-12-01, 1.11.0 2025-02-27, 1.12.0 2025-05-30, 1.13.0 2025-08-28, 1.14.0 2025-11-30, 1.15.0 2026-02-28, 1.16.0 2026-05-29, 1.17.0 2026-08-31 (87 to 94 days apart since 1.11.0). 18 tagged releases in the last 365 days. A minor release is published with the final patch of the previous line (1.17.0 and 1.16.4 at 18:12 and 18:11 UTC on 2026-08-31).
- Layout events per release (from the diffs in sections 2, 3, 6, 7):
  - Mon bits: 1.8.0, 1.9.0. Type IDs: 1.9.0. Species table prefix: 1.7.0 (names inline), 1.9.0 (`forceTeraType`). Item name inline to pointer: 1.13.0. Move names into `gMovesInfo`: 1.8.0. GF header pointers: 1.7.0, 1.8.0.
  - `struct SpeciesInfo` has 15 distinct texts across tags 1.4.0 to 1.17.2 (it changes at 1.7.0, 1.7.2, 1.8.0, 1.8.1, 1.8.2, 1.9.0, 1.9.1, 1.10.0, 1.12.0, 1.13.0, 1.14.0, 1.15.0, 1.16.0, 1.17.0).   - SaveBlock1 differs in 7 groups: 0.9.0-1.4.3, 1.5.0-1.7.4, 1.8.x (`FREE_*` conditionals), 1.9.0-1.12.3 (`roamer[ROAMER_COUNT]`), 1.13.0-1.14.4 (`struct Bag` wrapper), 1.15.x (FRLG-only fields), 1.16.0+ (`dailySeed`, 4 padding bytes after `giftRibbons`). SaveBlock2: 2 groups, change in 1.8.0.
  - `BattlePokemon`: 8 groups; changes of layout in 1.4.0, 1.8.0, 1.13.0, 1.16.0.
  - `gParties`: 1.16.0.
- Savefile impact is mentioned in the changelogs only occasionally (1.8.0 "SaveBlock3 ... save-compatible"; 1.9.0 "`ROAMER_COUNT` is set to 1 to keep save compatibility"; `species_enabled.h` and `save.h` comments).

## Open gaps

- No real expansion-hack ROM was inspected. The RHH block offset is derived as 0x08000204 but third-party numbers are 0x1FC and 0x200; the cause is unknown.
- Struct sizes other than the mon structs were not computed (`SpeciesInfo`, `MoveInfo`, `ItemInfo`, `BattlePokemon`, `Volatiles`): that needs `arm-none-eabi-gcc -mabi=apcs-gnu` with the real headers. The mon-struct bit positions were checked under clang's default ARM rules, not the Makefile's ABI. The width of unpacked enums in bitfields (`cryId`, `natDexNum`) is therefore unresolved.
- Run & Bun, Emerald Imperium and Lazarus: the authors' own statements on their base were not readable (PokeCommunity returned HTTP 403, `runandbun.com` failed TLS verification). Their expansion versions, their RHH blocks and the Imperium/Lazarus lineage come from third-party tools or search excerpts. Run & Bun's mon layout comes from third-party Lua only.
- Whether closed hacks keep, strip or move the RHH block is known only from one report (Dreamstone has none); how many released hacks on 1.7.x to 1.12.x lack it is unknown.
- Distribution format is unverified for Rogue, Inclement Emerald and Lazarus. Whether Imperium and Run & Bun ship as BPS or UPS was not read from a primary page.
- `ITEMS_COUNT` for 1.15.0 and later and `gBattleWeather` encodings for 1.9.x to 1.11.x were not computed.
- Whether the `eliteredux-source` default branch matches the released Elite Redux ROM was not checked. Which expansion version each Rogue release was built from is not established (branch says 1.7.4; releases `EX-v2.1` and pokedaisy's v2.2.1-EX differ).
- How hack authors that rebase onto newer expansion tags keep saves compatible (and so whether a hack's layout moves between its own releases) was not researched beyond the Heart and Soul and Rogue version fields.
- The exact `GetMonData` behavior for eggs and bad eggs in boxes (`IsBadEgg` rewrites `isEgg` flags on read) was read but not exercised.
