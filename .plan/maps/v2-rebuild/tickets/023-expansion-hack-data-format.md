# Expansion hack data format

## Question

Does v2.0 support hacks built on pokeemerald-expansion, and if so, how does it decode them?

[ROM hack name tables](./020-hack-name-tables.md) lets a profile describe expansion name tables, but these hacks also change struct layouts, and the size of `gSpeciesInfo` entries depends on build config. Decide whether expansion becomes its own data format with its own decoder, how a profile gets per-build strides and field offsets (symbol or map files, a build-time generator, hand entry), which hacks are in reach given that closed ROMs ship no symbols, and what v2.0 says about expansion hacks if support waits.

## Answer

v2.0 ships no data format or profile for expansion hacks. It refuses every ROM where it finds the expansion version block, and a hash or signature mismatch keeps hacks whose header or table pointers differ from retail from loading an official profile without a manual pick. Support waits for a later map, which can start from [the research](../assets/023-expansion-hack-data-format.md).

- **Scope.** v2.0 has no data format or profile for expansion hacks, or for other hacks whose mon layout differs from the official games', such as Run & Bun, Emerald Imperium, Elite Redux, Inclement Emerald and Emerald Rogue. A manual pick of an official profile on such a ROM, or a header match under the gap described below, still reads it with vanilla layouts unless the program finds the block. The signature warning below is the only guard on a manual pick. The map Notes' "decomp-based hacks" now means decomp builds that keep the official Gen 3 layouts. Expansion hacks don't share one layout. Run & Bun appears to be an early expansion hack without the block and with its own bits (unverified, from third-party scripts and its published data), and hacks on one expansion version can widen fields. Neither expansion nor any hack checked publishes symbols. Battle state changed layout or encoding in 1.8.0, 1.9.0, 1.11.0, 1.13.0, 1.15.0, 1.16.0 and 1.17.0. 1.14.0 and 1.15.0 also retyped battle fields as enums, and the volatile status list changed in 9 of the 21 tag steps from 1.13.0 to 1.17.2. Under [Game profile source and format](./005-game-profile-source.md), a new data format is a code change and a release, so deferring rules nothing out. The later map decides whether expansion becomes one data format or several, and where its per-build strides and field offsets come from, since no ROM header carries them.
- **Detection.** At identification the program scans ROM from `0x08000100` to `0x08000400` in 2-byte steps for the `RHHEXP` magic. From expansion 1.7.2 the block follows the GF ROM header, near `0x08000200`, though its exact offset is unconfirmed. In 1.7.0 and 1.7.1 it may sit outside the scan, hacks built on expansion before 1.13.0 can lack it, and hacks built before 1.7.0 have none. Those hacks rely on the hash and the signature, apart from the header-match gap below. No v2.0 data format accepts expansion hacks, so a ROM where the scan finds the block loads no profile, whether by hash, header or manual pick. It stays `unidentified`, and the viewer names the expansion version and says v2.0 doesn't read it. A later expansion data format will be the only kind such a ROM may load.
- **Status.** `status.rom` gains `expansion: { version, tagged } | null`. `version` is `"<major>.<minor>.<patch>"` from the block, and `tagged` is bit 0 of its flags byte. A hack built from an untagged expansion commit reports the next patch number with `tagged: false`. `null` means the scan found no block in its range or the adapter can't read ROM, not that the ROM isn't an expansion hack.
- **Vanilla signature.** Each official Gen 3 profile carries a `signature` of the GF ROM header words that point to the species, item and move tables. The generator writes their expected values from pret symbols. `bun run test:local`, which [Decoder test fixtures](./014-decoder-fixtures.md) defines to read the owner's local files and never run in CI, must confirm each signature against the owner's retail ROM before it ships, and a signature that fails it is a profile bug. If a game has no GF ROM header, the owner picks other retail bytes with the dev script that [Game identification](./009-game-identification.md) uses for Gen 1-2 header values. The program checks the signature of every profile that declares one, whatever the match path. A header match whose signature fails, or can't be read, counts as a modified ROM, as a hash mismatch already does, and stays `unidentified` until a manual pick. CFRU repoints the species-data pointer stored at `0x080001BC`, which [the hack reference data research](../assets/010-hack-reference-data.md) confirms from CFRU's repoint lists, and expansion hacks are expected to move all three tables because their tables grow, which is an inference. The signature should therefore catch both on emulators that give no hash, but no hack ROM has been checked, and a `test:local` run against the owner's hack ROMs confirms it.
- **Header matches.** A header plus signature match still loads its profile without a manual pick. `status.game.match` already says how the ROM matched, so when it is `"header"` the viewer shows a small note that the ROM matched by header, and by signature where the profile has one, not by hash. A hack that changes struct layouts but keeps the retail header and the three table pointers passes the signature and loads the official profile. That is a known gap. Expansion hacks whose block the scan finds can't fall into it.
- **Manual picks.** On a ROM without a detected block, a manual pick of an official profile loads even when the signature failed. `status.game` gains `signature: "match" | "mismatch" | "unchecked" | null`, a closed enum. `"unchecked"` means the program couldn't read a signature word, as when the adapter can't read ROM, and `null` means the profile declares no signature, as in Gen 1-2. When `match` is `"manual"`, the viewer warns on `"mismatch"` that the ROM's data tables moved and values may be wrong, and on `"unchecked"` that the program couldn't check the ROM. After an exact hash match, a `"mismatch"` means the profile's own signature is wrong, so the program logs a profile error and the viewer shows no table warning. Randomizers that leave the tables in place pass the signature and show no warning. Without ROM reads the program can't detect the block, so a pick there loads with `"unchecked"` and its warning.
- **Name tables.** The `pointer` name kind from [ROM hack name tables](./020-hack-name-tables.md) is dropped. Only expansion 1.8.0 and later use it, and no v2.0 profile can load those hacks. `name` is `{ kind: "inline", length }` only. A later expansion data format can add `pointer` back without breaking existing profile files.
- **Hacks in reach.** CFRU hacks use the CFRU data format. Hacks that keep the official Gen 3 mon and save layouts use the Gen 3 data format, through a hack profile or a manual pick of the official profile, whether they were made by editing a retail ROM or built from pret's decomp. Name-table strides are profile data under ROM hack name tables, and game-state struct strides and field offsets stay in decoder code, so these profiles supply addresses, constants and name tables only. The generator also accepts the `.sym` file that `make syms` writes for a hack build, and records the hack, its version and the file's SHA-256 as provenance. It reads no `.map` files, since anyone who can build the hack can run `make syms`. v2.0 ships no address finder, so a hack release without a matching `.sym` needs its addresses found by hand. A smoke fixture catches a self-built `.sym` that doesn't match the released ROM.
- **Species data.** No decision yet gives hack profiles a source for per-species data such as gender ratio, ability slots, growth rate and National Dex number. Until a new ticket, Hack species data, resolves, a `kind: "hack"` profile gives `null` for `gender`, `ability` and `species.dex` on every Pokémon in a party or box, for `species.dex` on battlers, and for a boxed mon's `level`, and the docs list these fields. A battler's `ability` comes from battle memory and stays. The new ticket decides where hack profiles get this data and when the fallback goes.

Amends [Game identification](./009-game-identification.md) (the vanilla signature on official Gen 3 profiles, the expansion block rule, the viewer's header-match note, `status.game.signature`, and signature bytes from its dev script for games without a GF ROM header), [API v2 contract](./006-api-contract.md) (`status.rom.expansion`, `status.game.signature`, and the `null` fallback for `gender`, `ability`, `species.dex` and a boxed mon's `level` on hack profiles), [ROM hack name tables](./020-hack-name-tables.md) (no `pointer` kind), [Game profile source and format](./005-game-profile-source.md) (the generator reads a hack's `.sym`), [Decoder test fixtures](./014-decoder-fixtures.md) (`test:local` checks each signature against the owner's ROMs), and the map Notes' Games line, whose decomp-based hacks become decomp builds that keep the official Gen 3 layouts.

Excluded: decoding expansion hacks in v2.0, per-hack data formats for named hacks such as Run & Bun, one expansion data format for the 1.9.0+ mon layout, struct layouts declared in profiles, checking only for the `RHHEXP` block before the header fallback, leaving the header fallback unguarded, making header plus signature matches wait for a manual pick, loading any profile on a ROM where the scan found the block (with or without a warning), refusing official profiles on ROMs that fail the signature, a silent pick on a failed signature, logging the expansion version without an API field, an open `warnings` list on `status.game`, keeping the unused `pointer` kind, reading `.map` files, an address finder script, hand entry as the only address source, and holding hack profiles until Hack species data resolves.
