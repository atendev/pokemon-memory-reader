# Release pipeline

## Question

How do the per-OS executables get built, shipped and updated, and how do emulator bridges reach the user?

Decide CI and cross-compile for Windows, Linux and macOS best effort, code signing and Windows SmartScreen, auto-update or not, where releases live, and how the mGBA and BizHawk Lua bridges are delivered and installed (see [Emulator memory access APIs](./001-emulator-memory-access.md)). The one-executable stack is from [Language and HTTP stack](./004-language-and-toolkit.md).

Input from [Decoder test fixtures](./014-decoder-fixtures.md): the v2.0 release checklist must include reviewing the coverage guard's printed list of tier 2 gaps and profiles with no fixture.

Input from [Importable package for overlay developers](./015-importable-package.md): `@pokemon-memory-reader/api` publishes to npm with provenance, alongside v2.0 but from a workflow that can run separately from the app release, because the two version independently. `2.0.0-rc.N` goes out under the `next` dist-tag and is promoted to `latest` at v2.0. CI runs `publint` and `attw` on the packed tarball and checks that the compiled executable works with `api/dist` absent. The owner claims the `pokemon-memory-reader` npm org before the first release candidate.

## Answer

v2 ships as unsigned per-OS archives on GitHub Releases, built and smoke-tested by GitHub Actions from a version tag, published by the owner from a draft after a committed checklist. The program checks for updates and shows a banner but never replaces itself. Bridges are embedded in the executable, written to a per-user data folder, served over HTTP for download, and also attached to each release.

- **Where releases live.** GitHub Releases on this repo, nothing else at v2.0. winget, Scoop, AUR and Homebrew can come later, and none blocks v2.0.
- **Targets.** `bun-windows-x64-baseline`, `bun-linux-x64-baseline`, `bun-darwin-x64-baseline`, `bun-linux-arm64`, `bun-darwin-arm64` and `bun-windows-arm64`. x64 builds use Bun's baseline variant because the default variant crashes on CPUs without AVX2, and the program isn't CPU-bound. Windows and Linux x64 are supported. Linux arm64, Windows arm64 and both macOS targets are best effort. Bun 1.4.2 compiled all six targets from Linux in a check on the owner's machine. Before writing the workflow, the implementer confirms the target list against `bun build --help` for the pinned Bun version.
- **Where builds run.** An ubuntu runner compiles the Windows and Linux targets. A macOS arm runner compiles both macOS targets and ad-hoc signs them with `codesign --sign -`, because arm64 macOS refuses unsigned binaries. No hardened runtime and no JIT entitlements. Each archive is then smoke-tested on the matching native runner: `windows-latest`, `windows-11-arm`, `ubuntu-latest`, `ubuntu-24.04-arm` and `macos-latest`. When writing the workflows, the implementer confirms that the arm runners are free for this public repo, and a target whose runner isn't available is marked untested in the release notes. darwin-x64 runs on the arm runner under Rosetta 2 (`arch -x86_64`), installed with `softwareupdate --install-rosetta --agree-to-license` if missing, and the release notes say it was tested under Rosetta only. The smoke jobs test the exact archives the release uploads, never rebuilds.
- **Smoke script.** `scripts/smoke.ts` runs in PR CI on linux-x64 and in every release smoke job. It takes the executable path and the expected version as arguments. Release jobs pass the version from the tag, and PR CI passes the version from `server/package.json`. The semver part of `--version`'s output must equal the expected version. The executable then starts with `--no-browser` on a free port picked by the script, with its data folder pointed at a fresh temp directory. `GET /api/v2/status` must return state `disconnected`. `GET /` must return the viewer HTML. `GET /bridges/mgba.lua` and `GET /bridges/bizhawk.lua` must return 200, and both files must exist in the temp data folder. Linux and macOS jobs then send SIGTERM and require exit code 0. Windows jobs end the process with `taskkill /F` in a `finally` step so a failed probe never leaves the port held, and they don't check the exit code. No test-only flag ships in the product.
- **PR CI.** `ci.yml` runs on push and pull request with a frozen install, Biome, `tsc --noEmit`, `bun test` (coverage guard included), the API package check (`bun pm pack`, then `publint` and `attw` on the tarball), and a linux-x64 compile with `api/dist` absent followed by the smoke script.
- **Signing and SmartScreen.** v2.0 ships unsigned on Windows and ad-hoc signed, not notarized, on macOS. The README and every release body give the SmartScreen step (More info, then Run anyway) and the macOS step (`xattr -d com.apple.quarantine <file>`), with the same notes for Windows arm64. They also mention that antivirus tools sometimes flag Bun-compiled executables, and the owner submits a flagged release to Microsoft's false-positive portal. Every release carries `SHA256SUMS`. After v2.0 the owner applies to SignPath Foundation for free OSS Windows signing. The project qualifies with a GPL license and a public build. That application is a follow-up outside this map, listed under Out of scope.
- **Archives.** One archive per target, named `pokemon-memory-reader-v<version>-<os>-<arch>.<ext>`: `.zip` for Windows and macOS, `.tar.gz` for Linux so the executable bit survives. Each holds the executable, `LICENSE`, `README.md` and `THIRD-PARTY-NOTICES.txt`.
- **Third-party notices.** `scripts/notices.ts` walks the production dependency closure of `server/` and `viewer/`, adds Bun's runtime license and its bundled components (the executable embeds the runtime), and adds fonts and other assets the viewer bundles. It writes `THIRD-PARTY-NOTICES.txt` with each license text. CI fails on a missing license or one outside a GPL-3.0-compatible allowlist (MIT, ISC, BSD-2-Clause, BSD-3-Clause, Apache-2.0, 0BSD and similar). An `OR` expression passes if one of its options is on the allowlist. The viewer's About page serves the same file.
- **Updates.** At startup and every 24 hours, the program lists this repo's releases through the GitHub API (`GET /repos/{owner}/{repo}/releases`, which hides drafts) and considers only app tags, `v` followed by a semver version, so `api-v*` releases and `v1-lua` never count. When a newer version exists it prints one console line and the viewer shows a banner linking to the release page, never to a specific asset, so a change in asset names can't break the link. The user downloads by hand. The check sends no user data, fails silently when offline or rate-limited, and is on by default with a config setting to turn it off. The README says so. Version comparison uses real semver ordering, so `rc.2` sorts before `rc.10`. A stable build compares only against non-prerelease releases. A prerelease build compares against all of them.
- **Channel.** The semver prerelease suffix is the channel. `--version` prints the version, target and short commit SHA, for example `2.0.0-rc.1 (windows-x64-baseline, a1b2c3d)`. CI injects the version and SHA with `--define`. A local build prints `dev` in place of the SHA. A GitHub release is marked prerelease exactly when its tag contains `-`.
- **Bridge delivery.** The bridges are embedded in the executable. On startup the program writes them to a per-user data folder: `%APPDATA%\pokemon-memory-reader\bridges\` on Windows, `$XDG_DATA_HOME/pokemon-memory-reader/bridges/` on Linux (falling back to `~/.local/share`), and `~/Library/Application Support/pokemon-memory-reader/bridges/` on macOS. It overwrites them when the program version differs. If the write fails, the program logs it once and carries on. The bridge files are `mgba.lua` and `bizhawk.lua`. The program also serves each one at `GET /bridges/<name>.lua` from an allowlist of known names, so no request path reaches the filesystem. The release workflow attaches the same `.lua` files as release assets for users who run the emulator on another machine. Bridge, archive and assets all come from the same commit.
- **Bridge install steps.** The viewer's connection screen shows the data-folder path with a copy button, a download button per bridge, and steps per emulator. mGBA: Tools > Scripting > File > Load script, with a note that 0.11 and later can pass `--script`. The `--script` note depends on mGBA 0.11 shipping that flag, and the implementer checks it against the release before writing the step. BizHawk: the exact `--lua=<path>` command line, or loading the script in the Lua console. RetroArch: enable network commands on port 55355.
- **Bridge compatibility.** Each bridge opens with a hello carrying a bridge protocol version, an integer separate from the app version that bumps only on wire changes. The adapter refuses a mismatch. A bridge that sends no hello, such as an old or v1-style script, is reported as an unknown bridge. In both cases `status` lets the viewer tell the user to reload the bridge from the data folder or the download link. The new ticket [Bridge wire protocol](./022-bridge-wire-protocol.md) settles the hello and the rest of the protocol.
- **Versioning and tags.** App tags are `v<semver>` and API package tags are `api-v<semver>`, and each triggers its own workflow. `release.yml` triggers on `v[0-9]+.[0-9]+.[0-9]+*`, so the frozen `v1-lua` tag never starts it, and the workflow checks that the tag parses as semver. The app version lives in `server/package.json`. The release workflow fails if the tag doesn't match it, or if the tagged commit isn't reachable from `origin/main`. `CHANGELOG.md` at the root covers the app and `api/CHANGELOG.md` covers the package, both written by hand. The release body comes from the matching changelog section.
- **Draft releases.** `release.yml` builds, signs the macOS targets, smoke-tests, and creates a draft release holding the archives, the `.lua` files and `SHA256SUMS`. The workflow pastes the coverage guard's printed list of tier 2 gaps and fixture-less profiles into the draft body. The owner publishes the draft after the checklist, so the update check never sees an unreviewed build. A pushed tag is never moved or deleted. If the checklist fails, the owner deletes only the draft, the fix lands on main, and the next RC or patch version is cut.
- **Release checklist.** `RELEASING.md` is committed and holds the release steps and a checklist for v2.0 and every RC: review the coverage guard's tier 2 and no-fixture list in the draft body; confirm every smoke job is green, the baseline, arm and Rosetta jobs included; write the changelog section; check that the release body carries the SmartScreen, quarantine and antivirus notes and the best-effort and Rosetta-only notes; hand-test Ctrl+C shutdown on Windows; for an API release, confirm the npm trusted publisher is configured. Before `2.0.0-rc.1` the checklist also requires the npm org to be claimed and the `DEFAULT_BASE_URL` constants to be settled by [Config file](./019-config-file.md).
- **npm publishing.** `release-api.yml`, triggered by `api-v*` tags, publishes `@pokemon-memory-reader/api` through npm trusted publishing (GitHub OIDC) with provenance and no long-lived token. The workflow publishes with the npm CLI at 11.5.1 or later, because older npm versions and `bun publish` can't publish through OIDC. A version with a prerelease suffix goes to the `next` dist-tag, and a stable version goes to `latest`, so publishing `2.0.0` is the promotion. Trusted publishing covers only publishing, so any other dist-tag change is an owner-run `npm dist-tag` command with 2FA, described in `RELEASING.md`. Each `api-v*` tag also creates a GitHub release whose body comes from the matching `api/CHANGELOG.md` section, marked prerelease when the tag contains `-`. Trusted publishing needs the package to exist, so at implementation time an owner-run `wizard.sh` does three steps in order. It claims the `pokemon-memory-reader` org, publishes a placeholder `0.0.0` by hand and runs `npm deprecate` on it with "use @next until 2.0.0", then configures the trusted publisher for `release-api.yml`. The first publish sets `latest` to the deprecated `0.0.0` until v2.0, and the wizard says so. Every real version, `2.0.0-rc.1` included, goes out through OIDC. The workflow filename is part of the trust config and never changes.
- **Pinned toolchain.** Root `package.json` pins Bun's exact version, and CI reads it through setup-bun's version file. CI installs from the committed `bun.lock` with `--frozen-lockfile`. GitHub Actions are pinned by commit SHA, and Dependabot updates them. A Bun upgrade goes through a PR that runs the full release smoke matrix.
- **v1.** The current Lua script is tagged `v1-lua` on main before any v2 code lands. v1 GitHub releases stay up, and their notes are marked legacy. v2 development merges to main, and there's no long-lived v1 branch. The v2 README links to the `v1-lua` tag.

Input to [Config file](./019-config-file.md): an update-check on/off setting (default on), a `--port` flag, `--no-browser`, a data-folder override (flag or env) that the smoke script uses, and clean shutdown with exit code 0 on SIGINT and SIGTERM, plus Ctrl+C on Windows.

Amends [Viewer design](./008-viewer-design.md): the connection screen gains the bridge path, copy and download buttons and per-emulator steps above; the app gains the update banner; Settings or an About page shows the version string and `THIRD-PARTY-NOTICES.txt`.

Signing costs money or an approval, so neither blocks v2.0, and the docs cover the warnings. Drafts give the owner a gate between a green build and a public release, which is where the fixture coverage review fits. Embedding the bridges keeps them matched to the program with no extra download for the streamers and runners this program serves.

Excluded: package managers at v2.0, a website or CDN, cross-compiling macOS on Linux, the default (AVX2) x64 builds, paid Windows signing or Apple notarization at v2.0, bare executables, a self-updating executable, no update check at all, bridges only as release assets, release-please or changesets, lockstep app and package versions, npm automation tokens, a dist-tag promotion workflow, publishing `rc.1` by hand without provenance, auto-publishing releases, moving or deleting pushed tags, a test-only exit flag in the product, and a long-lived v1 branch.

Amended by [Icon loading and fallbacks](./021-icon-loading.md): `RELEASING.md` runs `check-icon-map` whenever the pinned sprites SHA changes and blocks the release until it passes.

Amended by [Bridge wire protocol](./022-bridge-wire-protocol.md): the program generates the bridge files with the configured host and port and rewrites them whenever the generated content differs, not only when the version changes.
