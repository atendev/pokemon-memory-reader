# Read loop and latency budget

## Question

How often does the program read each resource from the adapter, how does it detect changes to push, and what is the latency budget from a game change to an SSE event?

Decide polling cadence per resource and per adapter, change detection (hash of raw bytes versus decoded compare), batching reads, behavior while the emulator is paused or fast-forwarded, and backpressure for slow clients. Events carry whole resources, per [API v2 contract](./006-api-contract.md).

Input from [Battle tracker data model](./012-battle-tracker-data-model.md): `battle` changes every turn (HP, PP, stat stages). There is no separate rate for it, but the poll rate must push `battle` within one poll tick of a turn change, and unchanged resources are never re-sent.

## Answer

The program runs one global tick loop that reads only what is demanded, detects changes in two stages, and pushes whole resources over SSE. A game change reaches a client in about 40 ms typically and 73 ms at worst, outside box cycles.

- **Loop.** One tick loop at `pollHz`, default 20 (50 ms), range 5-60. A cycle that overruns skips the missed ticks and never queues. The effective interval is the larger of `1000 / pollHz` and the adapter's declared `minIntervalMs`. An out-of-range `pollHz` is clamped with a logged warning, not a startup error. A warm GET serves the cached value without touching the adapter. Cold-resource and stale-box GETs are the only exceptions, described below.
- **Demand.** Only resources with an SSE subscriber or a GET in the last 5 s are read. `status` and the in-battle flag are always read. `battle` also counts as demanded for as long as the in-battle flag is set, so `lastBattle` is complete when nobody is subscribed. A GET on a cold resource runs one extra cycle at once, serialized with the loop, and waits for it. The cold read runs right after the current main batch and ahead of any box request that hasn't started yet. If a box request is already in flight, the cold cycle waits for it to finish, which the 1000 ms box timeout bounds. The 250 ms read timeout then counts from the start of the cold read itself, so a cold GET takes at most about 1.25 s (a box request in flight, then the cold read) and otherwise at most about 500 ms, and the wait behind a box request never counts toward that timeout. Cold GETs that arrive together share one cold cycle, so the bounds hold for each of them. An SSE subscriber to a cold topic gets the same extra cycle and receives the first decoded value as its on-connect event. A request with no game loaded, or a cold read that times out or returns nothing, gets a `503` on GET, and the stream holds the topic, per the API contract.
- **Boxes.** Read only when demanded and at most once per 1000 ms (`boxesMinIntervalMs`, internal), in their own request, serialized after the main batch within the same cycle. The main batch's results are decoded and emitted before the box request starts, but a game change that lands during the box read waits for it. The box read lengthens that cycle, and a longer cycle skips ticks as usual. The box request has its own 1000 ms timeout, so a box cycle can delay a change by up to that long on top of the budget. This deliberately relaxes the battle tracker's one-tick rule on box cycles only, which exist at most once a second and only while boxes are demanded by an SSE subscriber or a GET in the last 5 s. The latency budget and its p99 target below exclude box cycles only: they and the one-tick rule hold on every other cycle, even while boxes are demanded, and a box timeout does not count toward the stall flag. A GET on a cache older than 1 s triggers one immediate box read and waits for it. The read follows the cold-read ordering: right after the current main batch, ahead of a box request that hasn't started. The wait is at most the 1000 ms box timeout plus a cycle already in flight, so about 2.25 s at worst. If that read times out, the GET returns the stale cache rather than a `503`, since boxes had data before. SSE subscribers get pushes at 1 Hz at most. Boxes can reach about 33 KB, which is too much to move at tick rate.
- **Batching.** Each cycle takes the union of the decoders' declared ranges for demanded resources, merges ranges within a domain only, and calls the adapter once with the whole list (boxes are the one separate call, at most once a second). The merge gap is an adapter-declared internal constant, default 32 bytes. Each adapter implements the batch natively or by pipelining. RetroArch sends one datagram per range, respects its 16384-byte and one-descriptor limits, and may raise its merge gap to cut the datagram count. Its slices may come from different frames, and it matches each reply to its request by the address the reply echoes, a format the RetroArch adapter spike confirms.
- **Change detection.** Compare each resource's raw slice bytes to the last tick's and skip decoding when equal. Otherwise decode, deep-compare the decoded JSON to the last emitted value, and emit only when it differs. The in-battle flag is part of the `battle` raw key, so a flag change always forces a decode. The first successful decode always emits and doubles as the on-connect value. A decode or validation failure emits nothing and leaves state unchanged.
- **Consistency.** The in-battle flag is read in the same batch. While the flag is set and battle data fails validation, keep the last valid state (inactive until the first valid read), emit nothing, count it, and retry next tick; this matches the battle tracker rule that `active` needs both the flag and valid data. Warn in the log after 2 s of consecutive failures. `{ active: false, lastBattle }` goes out only after the flag reads clear, and carries the last valid battle snapshot. Other resources rely on their decoder's own checks, such as the Gen 3 checksum. No debounce, no double read.
- **Pause and stalls.** Each batch has a 250 ms timeout. A timeout means no data this tick: keep the last values and emit nothing. After 1 s of consecutive timeouts, `status.adapter.stalled` becomes `true`, an additive field cleared on the next good read. A cold read's timeout counts toward it like any other main-batch timeout. mGBA and BizHawk are disconnected only when the socket closes, which is the only disconnect signal, so a paused emulator keeps its data indefinitely. RetroArch (UDP) is disconnected after 30 s without a reply, since streamers pause for longer than 10 s and a disconnect would blank their overlays. Replies must be correlated to requests (by id for the bridges), and a late reply after a timeout is discarded and never used as the current sample.
- **Fast-forward.** No special handling. The loop samples on wall-clock ticks, so intermediate states can be missed at high speed. The API docs list this as a limitation.
- **Slow clients.** Each SSE client holds at most one pending event per topic, and latest wins: a newer event removes the queued one and goes to the tail. There is no cross-topic ordering promise. On-connect values and `status` follow the same rule. A client whose socket stays unwritable for 30 s is closed as a normal end of stream, and its `EventSource` reconnects and receives the on-connect values. This is consistent with the stream never emitting an error event. A comment heartbeat goes out every 15 s.
- **Latency budget.** From the emulator frame where the game changes to the SSE write on localhost, at the default 20 Hz: the tick wait averages 25 ms and tops out at 50 ms, the frame-gated reply takes up to about 17 ms (8 ms on average), decode and diff take under 5 ms, and the write about 1 ms. That is about 40 ms typical and 73 ms worst case, and the target is a p99 of at most 100 ms to leave headroom for scheduling jitter. All figures exclude stall, timeout and box cycles. Outside box cycles, `battle` lands within one tick, counting the cycle's own read. On a box cycle, which happens at most once a second and only while boxes are demanded, add the box read time, capped at the 1000 ms box timeout and measured in the adapter spikes. The figures assume one frame per RetroArch reply, which holds only if the range count stays small (see the open item below), and they scale with `pollHz`: the tick wait is `1000 / pollHz` at most, so 5 Hz can add 200 ms.
- **Observability.** Counters for tick, read and decode duration, skipped ticks, per-client drops and validation failures are served at `GET /debug/metrics` only under `--debug`, outside `/api/v2`, with no stability promise. The public `status` gains only `stalled`.
- **Settings.** `pollHz` is the only new user-visible setting. The 250 ms timeout, 1 s stall threshold, 30 s UDP disconnect, merge gap, 5 s warm window, 1 s boxes interval, 1000 ms box timeout, 30 s drain limit and 15 s heartbeat are internal constants.

Per-adapter cadence: every adapter uses the same `pollHz` and `minIntervalMs` defaults to 0. The RetroArch adapter spike sets a floor only if the measurement below needs one.

Open for implementation, not for the spec: confirm that paused mGBA, BizHawk and RetroArch really stop replying, and whether RetroArch handles one command or all pending commands per poll. If it handles one per frame, N merged ranges cost N frames and the RetroArch budget holds only with a larger merge gap. Measure this in the RetroArch adapter spike.

A single tick keeps the bridge adapters' resources from one sample (RetroArch's pipelined slices can span frames), keeps warm GETs off the adapter, and bounds the load an idle overlay costs. Two-stage detection keeps decoding off the hot path without emitting on bytes that don't change the resource.

Excluded: per-resource cadences, reading on every GET, always reading every resource, reading the full WRAM block, hashing raw bytes only, decoded-only comparison, double-read or debounce before emitting, treating a timeout streak as a disconnect, unbounded per-client queues, dropping slow clients on buffer size, timing fields in the public `status`, and exposing the internal constants as settings.
