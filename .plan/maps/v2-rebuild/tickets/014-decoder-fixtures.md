# Decoder test fixtures

## Question

How do decoders get tested against real game data without committing ROMs?

The owner can produce savestates and RAM dumps, and the [License](./007-license.md) decision allows only trimmed RAM slices in the repo. Decide the slice file format, which game states to capture per data format (party, bag, battle, boxes, edge cases), the tool that cuts a slice from a local dump, and how tests run without the local dumps.

Input from [Battle tracker data model](./012-battle-tracker-data-model.md): battle fixtures must confirm the Gen1 and Gen2 `wEnemyMon` DV read, an Emerald multi or in-game-partner battle (whether partner mons sit in player party memory), a turn counter address per generation if one exists, each `modes` value shipped in v2.0, and a double battle with a partner, and the Gen1 and Gen2 prize formulas against `wAmountMoneyWon` and `wBattleReward` after a win, and the Gen1 and Gen2 `wBattleResult` mask and outcome mapping against won, lost, drew, ran and caught savestates.

## Answer

Decoders are tested against **fixtures**: trimmed memory **slices** (one recorded memory range each) captured live from the owner's games through the real adapter, committed as one JSON file per game state with a reviewed golden file of the decoded resources beside it. The default suite runs only on committed fixtures and synthetic buffers. Nothing in it reads a savestate, a dump or a ROM.

- **Fixture file.** `<state-slug>.fixture.json`, checked by a Zod schema. Metadata: profile ID, data format, emulator and version, adapter name, capture tool version, capture date, `anonymized`, and a free-text description of the in-game state. `regions: [{ domain, offset, length, sha256, bytes }]`, with `bytes` in base64. The sha256 shows whether a recapture changed the bytes or only the file format. Regions use the adapter interface's logical domains (GB `wram`, `hram`, `sram`; GBA `ewram`, `iwram`), never emulator addresses.
- **No ROM bytes.** No fixture holds ROM data. Decoders that read ROM tables (trainers, trainer class names, the money table, hack name tables) and header identification are tested on synthetic byte buffers built in the test, plus optional local tests against the owner's ROM. Those resources have no real-data golden, and the docs say so. Fixtures hold no ROM, so in fixture tests the profile's ROM tables count as missing and the fields that depend on them decode to null, as [Battle tracker data model](./012-battle-tracker-data-model.md) already requires for a missing table. Goldens record those nulls, and the fields never go on a `verified` list. Committing small ROM slices and committing decoded ROM tables as JSON were both rejected: the first breaks the no-ROM rule, and the second is a derived copy of ROM content.
- **Declared reads.** Each decoder declares what it reads as a function of the profile, in two phases: static regions `{ domain, offset, length }` and pointer-derived regions `{ ptrEntry, length }`. Lengths cover the maximum (a full party, all boxes), never only what the current state uses. The capture tool records the union of the declared reads for the requested resources, including the pointer words, so a test can repeat the same two-step read.
- **SliceAdapter.** In tests, a `SliceAdapter` implements the adapter interface over a fixture and throws on any read that falls outside a recorded region. A decoder that reads undeclared memory fails loudly instead of decoding zeros.
- **Capture tool.** `bun run fixture:capture <profile-id> <state-slug>` connects to a running emulator through the real adapter, resolves the declared regions from the profile, reads them and writes the fixture plus a draft golden file. The owner loads a savestate first. `--from-dump <domain>=<file>` takes flat per-domain dumps instead of a live emulator. `--append` adds a frame to a sequence fixture. `--anonymize` overwrites the player name, OT names and trainer ID bytes and sets `anonymized: true`, and the golden is written after anonymizing. In Gen 3 it picks a new trainer ID and secret ID whose XOR equals the original, so shininess holds, then fixes each mon's checksum. Gen 1-2 shininess comes from DVs, so it's unaffected. Gen 1-2 SRAM save checksums are left as they are, since the program doesn't verify them. Fields the anonymizer rewrote never go on a `verified` list. Fixtures that prove checksum, shiny or gender behavior are not anonymized. Savestate files are not parsed: mGBA, BizHawk and RetroArch formats differ, and the savestates stay local as the source to recapture from. Capturing through the adapter can bake an adapter bug into a fixture, so when it's practical, one state is also captured on a second emulator and the bytes are compared.
- **Golden files.** The capture tool writes a draft as `<state-slug>.expected.draft.json`. Only the owner promotes it to `<state-slug>.expected.json`, after checking it against the game. The coverage guard fails if a draft file is committed. `<state-slug>.expected.json` holds the decoded resources and a `verified` list naming the fields the owner confirmed on the in-game screens (summary, bag, box, battle). Fields not on that list are unverified, so the golden doesn't claim more than was checked. Tests compare with deep equality. An agent never regenerates a golden without a human-reviewed diff. Bun snapshots were rejected because `--update-snapshots` lets wrong output be accepted without review. Targeted assertions cover facts a golden can't express.
- **Sequence fixtures.** `<slug>.sequence.json` holds ordered `frames`, each in the fixture schema, with the expected resource state per frame. They test battle start and end: an intro frame that doesn't validate, then a valid frame; the last in-battle frame, then the post-battle frame where the outcome is read; and Gen 1 `wIsInBattle == 0xFF`. Frames are separate savestate loads, so these tests check transition logic on ordered states, not real frame timing. The invalid intro frame may instead be made by mutating a real frame.
- **Synthetic mutations.** Test helpers mutate real slices to reach states real data rarely covers. They re-encode a Gen 3 mon under a different personality value (reorder, re-encrypt, fix the checksum) to cover all 24 substructure orders, flip a checksum byte for a corrupt slot, set the bad-egg flag, and write an invalid species ID into a Gen 1-2 box slot. A self-check proves the re-encoder correct: re-encoding a real mon under its own personality value must reproduce the original bytes exactly. Helpers never write fixture files. Every helper starts from a real slice's bytes and changes only what its case needs. A from-scratch test encoder that builds mons with no real bytes was rejected as the synthetic-only path the [License](./007-license.md) decision ruled out.
- **Layout.** `server/test/fixtures/<profile-id>/<state-slug>.fixture.json` with `.expected.json` and `.sequence.json` beside it, and kebab-case slugs that describe the state (`trainer-battle-turn1`). The profile ID implies the data format, so there's no data-format folder. No fixtures package ships; see [Importable package for overlay developers](./015-importable-package.md).
- **Primary revisions.** Each data format has primary revisions that carry the full matrix: Gen 1 `red-us-1.0`, Gen 2 `crystal-us-1.1`, Gen 3 `emerald-us-1.0`, `firered-us-1.0` (pointer save blocks, a different bag layout) and `ruby-us-1.0` (static addresses), and CFRU `radical-red-4.1`. Gen 3 has three because those games exercise different address shapes from one decoder. Every other revision the owner owns gets a smoke fixture (party and player) that checks its generated addresses and charmap. Yellow is smoke-only, since its addresses differ from Red's. A language counts as supported only after it has a smoke fixture, which covers its charmap.
- **Coverage matrix.** `server/test/fixtures/coverage.ts` lists the required states per data format, each tagged `tier: 1 | 2` and naming the fields its golden must list as `verified`. ROM-derived fields and fields an anonymizer rewrites are never named, so a state can always pass.
  - Tier 1: new game with an empty party; a full party of 6 with a status condition; a nickname with special characters; bag with every pocket non-empty; player (money, badges, name, playtime); boxes (Gen 3 storage with several boxes filled, Gen 1-2 current box plus at least one non-current SRAM box); a wild single battle on turn 1; a trainer single battle on turn 1 with a partly revealed party.
  - Tier 2: an egg (Gen 2-3); a Gen 1-2 capture after switching box without saving, to show staleness; a Gen 3 and CFRU trainer double battle; the battle intro frame that doesn't validate; and every verification fixture below.
- **Coverage guard.** A default-suite test fails when a tier 1 state is missing for any primary revision of a supported format, when a tier 1 golden's `verified` list lacks a field the matrix names, when a fixture has no golden file, or when a draft golden is committed. It prints, as one stable sorted list, the tier 2 gaps and the profiles with no fixture, so a new gap shows up in review. Tier 2 gaps never fail the suite. The v2.0 release checklist in [Release pipeline](./017-release-pipeline.md) must include reviewing that list.
- **Verification fixtures.** Each open fact from [Battle tracker data model](./012-battle-tracker-data-model.md) gets a named tier 2 fixture tagged `proves: "<fact>"` with a targeted assertion: the Gen 1 and Gen 2 `wEnemyMon` DV read; an Emerald multi or in-game-partner battle (whether partner mons sit in player party memory); a double battle with a partner; a turn counter address per generation; each `modes` value; the Gen 1 and Gen 2 prize formulas against `wAmountMoneyWon` and `wBattleReward` after a win; and the Gen 1 and Gen 2 `wBattleResult` mask and outcome mapping against won, lost, drew, ran and caught savestates. Until its fixture lands, a field keeps the fallback that decision defined: `turn` null, the mode left out of the v2.0 enum, partner `partySlot` null, Gen 1-2 `prizeMoney` null, and Gen 1-2 outcomes `unknown`. A mode that can't be captured (link needs two emulators, facility needs a post-game save) is dropped from the v2.0 enum instead of blocking the release.
- **Contradictions.** An internal correction such as a different mask or address is fixed in code and noted in the fixture's description. A finding that changes a public field's shape or meaning stops the implementer, who files a new ticket amending [Battle tracker data model](./012-battle-tracker-data-model.md) or [API v2 contract](./006-api-contract.md) and names the fixture slug as evidence. The field keeps its documented fallback until that ticket resolves.
- **Support gate.** A decoder may merge with synthetic tests alone. Whether a data format is supported is a committed `supported` flag in the decoder registry, and a test allows it to be true only when the tier 1 states pass, with their required fields verified, on every primary revision of that format. A profile whose format isn't supported loads, and its resources return `503 unsupported`. Each profile JSON carries a committed `fixture: "full" | "smoke" | "none"`, and a test checks it against the fixture folder. A `"none"` profile loads normally, and the program logs one warning per session naming the profile ID and saying it has no fixture. The API gains no field, because `match` already says how sure identification is, and an additive `status.game.verified` can follow if users ask. The docs list profile coverage from the same data. For CFRU and other hacks, `features.boxes` stays false until that profile has a box fixture.
- **Running tests.** `bun test` and CI read only committed fixtures and synthetic buffers. Tests that need the owner's savestates, dumps or ROM run under `bun run test:local`, which reads paths from env vars and never runs in CI. Local files live in a gitignored `fixtures-local/` folder. If an env var is unset, `test:local` prints a clear "not run" line. If a set env var points to a missing file, the test fails. Skipping tests when local files are missing was rejected because skips look green.
- **Size and privacy.** A default-suite test caps a fixture file at 256 KB and a sequence file at 1 MB, which fits Gen 3 full storage plus party and battle regions. There is no Git LFS. Fixtures may carry the owner's trainer name and IDs unless captured with `--anonymize`.

Capturing through the adapter avoids parsing three savestate formats. Declared reads with a strict SliceAdapter keep the slices as small as the [License](./007-license.md) decision requires and make each decoder's memory footprint explicit. Reviewed golden files with a `verified` list keep real data honest without letting an agent bless its own output. Tiers keep the owner's capture work from blocking support for a whole format.

Excluded: committing ROM bytes or decoded ROM tables, parsing savestate files, whole-domain captures, a permissive fake adapter, Bun snapshots, committed draft goldens, skipping tests when local files are missing, a full matrix on every revision, failing the suite on tier 2 gaps, blocking v2.0 on every verification fixture, reopening resolved tickets, an API field for fixture coverage, always or never anonymizing, Git LFS, a from-scratch test mon encoder, and a data-format folder level.
