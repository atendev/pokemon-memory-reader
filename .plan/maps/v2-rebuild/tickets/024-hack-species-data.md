# Hack species data

## Question

Where do hack profiles get the per-species data that computed fields need, and when does the `null` fallback go?

[Expansion hack data format](./023-expansion-hack-data-format.md) gives `kind: "hack"` profiles `null` for `gender`, `ability` and `species.dex`, and for a boxed mon's `level`, because no decision gives them gender ratio, ability slots, growth rate or National Dex numbers. Official profiles use shipped reference data, and CFRU repoints the species data table behind header word `0x080001BC`. Decide whether hack profiles read species data from ROM the way they read name tables, what layout they declare, what these fields return when the table is missing, fails validation or the adapter can't read ROM, and how the `null` fallback is removed.

## Answer

A hack's game profile declares where its species tables sit in ROM. The program reads them with the name tables and computes `gender`, `ability`, `species.dex` and a boxed mon's `level` from them. The blanket `null` fallback from [Expansion hack data format](./023-expansion-hack-data-format.md) is removed. These fields are now `null` only when a table fails, its `base` doesn't resolve into ROM, the adapter can't read ROM, or a value falls outside its table, such as experience above the `maxLevel` entry or a `dex` entry of 0.

- **Source.** Species data is read from ROM, and the profile declares locations only, as [ROM hack name tables](./020-hack-name-tables.md) does for names. It follows each hack release without a re-dump and ships no data that hack authors created. Official profiles keep shipped reference data.
- **Profile.** Every `kind: "hack"` profile has a required `speciesData: { info, dex, exp }`. Each key is a table or the literal `"vanilla"`, which means shipped reference data and reports `"builtin"`. Zod rejects an omission. `info` and `dex` are `{ base, count }`, and `exp` is `{ base, maxLevel }`. `base` uses the 005 address form.
- **Layout.** Stride, field offsets and experience row length live in data-format code, as 005 says for struct layouts. The Gen 3 `info` entry has `genderRatio` at 0x10, `growthRate` at 0x13 and abilities at 0x16 and 0x17, and its experience rows hold 101 levels. CFRU uses the same entry with a u8 `hiddenAbility` at 0x1A, and its rows hold 256 levels. Both strides are 0x1C, which the research infers but no source states, so a ROM fixture must confirm it before either decoder ships. A `dex` entry is a u16, and entry `i` is species `i + 1`.
- **Computed fields.** `gender` uses `genderRatio`. The Gen 3 decoder picks the ability slot by bit 31 of the misc substructure's IV word, as the official games do. The CFRU decoder takes `hiddenAbility` when that bit is set and `hiddenAbility` is non-zero. Otherwise it takes slot 1 when `personality & 1` is 0 or slot 2 is empty, and slot 2 in every other case, as CFRU's `GetMonAbility` does. A boxed mon's `level` is `null` when its experience is above the `maxLevel` entry of its `growthRate` row. The program checks this first, so experience equal to that entry gives `maxLevel`. Otherwise the level follows pokefirered's `GetLevelFromBoxMonExp`: start at level 1, count up while the row entry for the mon's `growthRate` is at or below its experience and the level is at most `maxLevel`, then subtract 1. A result of 0, which only a corrupt or edited mon produces, gives `null`. That CFRU levels box mons with the same routine is inferred, and a boxed-mon fixture confirms it. `exp: "vanilla"` uses the six Gen 3 curves in code with `maxLevel` 100. Forms report their base species' National Dex number, and a `dex` entry of 0 gives `null`, as 006 gives for hack-only species. A battler's `ability` still comes from battle memory.
- **Load timing.** Species tables load in the same window as name tables, before `status.state` becomes `game`. They load in chunks of at most 64 KiB, the bridge's read cap, as name tables do. CFRU's tables are about 36 KiB for `info`, 2.6 KiB for `dex` and 6 KiB for `exp`. The schema caps `info` and `dex` `count` at 65535, since species IDs are u16. A table that fails doesn't hold the state back.
- **Validation.** Each table is checked as a whole and discarded whole if it fails, and the failure is logged. A `base` that doesn't resolve into cartridge space (`0x08000000`-`0x09FFFFFF`), such as a header pointer that holds garbage, counts as a failed table. So does an `info`, `dex` or `exp` table whose last byte (`base` plus `count` times the stride, or plus the six experience rows) lies beyond `0x09FFFFFF`. An `info` table needs the share of non-empty entries (base stat total above 0, entry 0 excluded) to meet the 90% constant from ROM hack name tables. Every non-empty entry needs `growthRate` of 5 or less and ability IDs, `hiddenAbility` included on CFRU, below the abilities name table's `count`, or below the vanilla Gen 3 ability count when abilities are `"vanilla"`. A `dex` table needs every value at or below a named `MAX_NATIONAL_DEX` constant, set to 1025, and its non-zero share must meet the same 90% constant. An `exp` table needs `maxLevel` below the data format's row length and all six rows non-decreasing from level 1 to `maxLevel`. The thresholds are rechecked against a real hack ROM.
- **Failure.** Nothing falls back to official data, because the hack's IDs and values no longer match. If `info` fails, `gender`, the party and box `ability` and a boxed mon's `level` are `null`. If `exp` fails, a boxed mon's `level` is `null`. If `dex` fails, `species.dex` is `null`. An adapter that can't read ROM makes every table the profile declares unavailable. The viewer's existing suggestion of a core that maps ROM covers these tables too.
- **Status.** `status.game` gains `speciesData: { info, dex, exp }`. Each value is `"builtin"`, `"rom"` or `"unavailable"`, a closed enum. Official profiles report `"builtin"` for all three in every generation.
- **Finding addresses.** `scripts/find-name-tables` becomes `scripts/find-rom-tables`. It also finds the `info` table by Bulbasaur's base stats, the `dex` table by its known opening values and the `exp` table by the Medium Fast row, then prints a `speciesData` fragment to review. The owner runs it against their own local ROM. A CFRU build without DPE may leave header word `0x080001BC` on the vanilla table, so `base` comes from the script's output, and a profile uses the header pointer form only when the owner confirms the header was repointed.

Amends [Expansion hack data format](./023-expansion-hack-data-format.md) (the blanket `null` fallback is removed), [API v2 contract](./006-api-contract.md) (`status.game.speciesData`, and `null` for these fields only on a failed or unreadable table or an out-of-range value), [ROM hack name tables](./020-hack-name-tables.md) (the script is renamed and species tables load in the same window), and [Game profile source and format](./005-game-profile-source.md) (the required `speciesData` block on hack profiles). It corrects [the hack reference data research](../assets/010-hack-reference-data.md): the `gBaseStats 080001BC` repoint line comes from DPE's `repointall`, not CFRU's.

Excluded: per-hack species JSON, keeping hack fields `null` permanently, an optional `speciesData` block, entry layouts declared in profiles, one combined species key, falling back to official data for a failed table, per-entry validation, capping hack levels at 100 with no experience table, extending the curves by formula past 100, a `rowLength` profile field, falling back to the code curves when `exp` fails, `null` for forms' dex numbers, and a separate species finder script.
