# Battle tracker data model

## Question

What is the shape of the `battle` resource and when does it flip between `{ active: false }` and active data?

Builds on [What battle state is readable](./011-battle-state-readability.md) and the `battle` resource in [API v2 contract](./006-api-contract.md). Decide the fields, how unknown or unreadable values are marked, and what the viewer's Battle screen shows when only part of the data exists, as in [Viewer design](./008-viewer-design.md).

## Answer

`battle` is a single shape for singles, doubles and two-opponent battles, split into a player side and an opponent side. It only goes active once the in-battle flag is set and the data decodes cleanly. Once the battle ends, the inactive shape keeps a frozen `lastBattle` snapshot with the outcome. The opponent's full party is exposed, each mon has a `revealed` flag, and the viewer hides unrevealed mons by default.

- **States.** Inactive is `{ active: false, lastBattle: LastBattle | null }`. Active is `{ active: true, battleId, kind, format, modes, turn, player, opponent, field }`. `lastBattle` is never carried while a battle is active. The resource is a union discriminated by `active`, as 006's `{ active: false }` already implied, and 006's key-stability rule applies within each variant. This amends the inactive shape in [API v2 contract](./006-api-contract.md) by adding a key.
- **When it flips.** It goes active when the in-battle flag is set (Gen1 `wIsInBattle` 1 or 2, Gen2 `wBattleMode` 1 or 2, Gen3 and CFRU `gMain.inBattle`) and the data validates: a non-zero opponent active species and a party count from 1 to 6. While the flag is set but validation fails, the resource stays inactive, and the program logs one de-duplicated warning per battle. There's no timer. The resource goes inactive again as soon as the flag clears, and the outcome is read on that transition. Gen1 `wIsInBattle == -1` (`0xFF`) is an end marker, not an in-battle value: the resource goes inactive with outcome `lost`. A test feeds an invalid frame sequence and asserts that the resource doesn't flip.
- **battleId.** A counter the program increments each time `battle` goes active. It appears on the active shape and on `lastBattle`. It resets to 0, and `lastBattle` becomes null, on a game change or a program restart. An adapter reconnect resets them only if the identified game changed, so a reconnect during a battle doesn't log the encounter twice. `.describe()` says the ID is unique only within one session.
- **Kind, format, modes.** `kind: "wild" | "trainer"`. Gen1 `wIsInBattle` and Gen2 `wBattleMode` use 1 for wild and 2 for trainer. Gen3 and CFRU use trainer when `gBattleTypeFlags & BATTLE_TYPE_TRAINER` (bit 3) is set and wild otherwise. `format: "single" | "double"`, set from `BATTLE_TYPE_DOUBLE` (bit 0). Gen1 and Gen2 are always `single`, and two-opponent battles are `double`. `modes: string[]` draws from a fixed enum of special modes mapped from each generation's flags. v2.0 ships only the values verified against fixtures (`safari`, `link`, `tutorial`, `facility`, `roamer`, `legendary`). More get added later without a breaking change. Unknown bits are ignored, and raw flag bits are not exposed.
- **turn.** `turn: number | null`, filled only where fixture work verifies a counter address. Otherwise null, which the viewer shows as `—`. The program does not count turns by watching state.
- **Sides.** `player: { active: Battler[], partner: Trainer | null }` and `opponent: { active: Battler[], party: OpponentMon[], trainers: Trainer[] }`. `active` holds one battler in singles and two in doubles, ordered by battler position. `trainers` is empty in wild battles, and two-opponent battles have two entries. In wild battles, `opponent.party` holds only the wild mons on the field: one in singles, and two in hack wild doubles.
- **Battler.** `{ position, owner: "player" | "partner" | "opponent", partySlot: number | null, species, level, types, hp, maxHp, status, ability, heldItem, moves, stats, statStages }`. `species`, `heldItem`, `status`, `stats` and `ability` use the same types as the `party` resource's Pokemon (`species` is `{ id, dex, name }`). Each move extends 006's `{ id, name }` with `pp` and `maxPp`. Values are live from the battle struct, so a Transformed mon shows the copied species, types and moves. The real mon sits at `partySlot`, in the `party` resource for the player side and in `opponent.party` for the opponent. `types` falls back to the species table if the struct has none. `statStages { atk, def, spa, spd, spe, acc, eva }` is normalized to −6..+6 in every generation, and Gen1's single Special stage fills both `spa` and `spd`. `ability` and `heldItem` are null where the generation lacks them. Every battler includes `stats`. Volatile statuses (confusion, substitute and so on) are left out of v2.0 and can be added later without a breaking change.
- **Partners.** `partySlot` indexes the side's party exactly as the game stores it. If Emerald multi or in-game-partner battles load the partner's mons into player party memory, `party` shows them during that battle, and its `.describe()` notes this. If the partner mons are not in party memory, `partySlot` is null for partner battlers. It is never null otherwise. [Decoder test fixtures](./014-decoder-fixtures.md) confirms which case holds, and the schema covers both.
- **OpponentMon.** The same `Pokemon` schema as the `party` resource, plus `partySlot`, `trainer: number | null` (an index into `trainers`, null for wild) and `revealed`. Gen1 and Gen2 wild mons are built from the battle struct. Their DVs fill `ivs`, so `shiny`, `gender` and `hiddenPower` are computed. `nickname` is filled where a buffer exists (Gen1 `wEnemyMonNick`). `evs`, OT name and OT ID are null. A fixture confirms the DV read before this ships.
- **revealed.** The program computes it. A trainer mon is revealed once any valid frame lists its party slot as the `partySlot` of an opponent battler. It stays revealed for the rest of the battle. HP below max also counts, as a proxy for a mon that was on the field before the program attached. A wild mon is always revealed. `.describe()` calls it best effort: if the program attaches mid-battle, a mon sent out earlier that is back at full HP reads as unrevealed.
- **Field.** `field: { weather, terrain, sides: { player: SideConditions, opponent: SideConditions } }`. `weather` is `"none" | "rain" | "sun" | "sandstorm" | "hail" | null`. `terrain` is `"none" | "electric" | "grassy" | "misty" | "psychic" | null`. `SideConditions` is `{ reflect, lightScreen, safeguard, mist: boolean | null, spikes: number | null }`. `null` means the generation or data format lacks the value: weather and spikes in Gen1, terrain outside CFRU, safeguard and mist in Gen1. `"none"`, `false` and `0` mean the value is tracked but inactive. Gen1's per-mon reflect and light screen bits map to the side of the mon that holds them. The CFRU rooms (Trick Room, Gravity and so on) wait until the `gNewBS` layout is read.
- **Trainer.** `{ id, classId, className, name, prizeMoney, items: Item[] | null }`. The profile locates optional ROM tables (`gTrainers`, `gTrainerClassNames`, `gTrainerMoneyTable`). A missing table leaves the fields that depend on it null and never raises an error. `prizeMoney` is the expected payout on a win, computed by the decoder. "Last mon" is the trainer's highest occupied party slot.
  - Gen1: `wTrainerBaseMoney` (BCD) × last mon's level.
  - Gen2: `wEnemyTrainerBaseReward` × last mon's level.
  - Gen3 and CFRU (`GetTrainerMoneyToGive`): `4 × lastMonLevel × gBattleStruct->moneyMultiplier × gTrainerMoneyTable[classId].value`, × 2 when `BATTLE_TYPE_DOUBLE` is set. Each trainer in a two-opponent battle gets its own amount.
  - Pay Day money is not included.

  The Gen1 and Gen2 formulas come from game knowledge and are confirmed with a fixture against `wAmountMoneyWon` and `wBattleReward` after a win. The field is null when any input is missing or `gBattleStruct` can't be read. `items` holds the remaining items in Gen2, the starting list in Gen3, and null in Gen1, and `.describe()` says which. In link, Tower and Frontier battles, fields that come from trainer tables are null.
- **LastBattle.** `{ battleId, outcome, endedAt, kind, format, modes, trainers, opponentParty }`. `endedAt` is an ISO 8601 UTC string from the program's clock. Everything except the outcome and timestamp is frozen from the last valid active snapshot, so HP is the last value read. `outcome` is `"won" | "lost" | "drew" | "ran" | "caught" | "forfeited" | "unknown"`.
  - Gen3 and CFRU mask `gBattleOutcome` with `0x7F`, then map 1 → won, 2 → lost, 3 → drew, 4 (ran) and 5 (player teleported) → ran, 7 → caught and 9 → forfeited. Anything else (mon fled, mon teleported, out of Safari Balls, CFRU additions) → unknown.
  - Gen1 and Gen2 mask `wBattleResult` with `0x3F`, then map 0 → won, 1 → lost and 2 → drew in trainer battles. In wild battles, 0 means won only if the wild mon's HP in the last snapshot was 0. Otherwise it's unknown, because those games don't tell running from catching in this byte. The mask and this mapping come from game knowledge, not from source. [Decoder test fixtures](./014-decoder-fixtures.md) confirms them with savestates. Lost and drew map the same as in trainer battles.

  The program never infers an outcome from party changes. `.describe()` lists which outcomes each generation can report.
- **Viewer.** With no battle, the screen shows the empty state, plus a one-line "Last battle" summary when `lastBattle` is non-null. Wild battles show a "Wild encounter" header with kind, format, modes and turn, and no trainer card. Trainer battles show one trainer card per entry in `trainers`, with `—` for null fields. A null name falls back to the class name, then to "Trainer". Kind, format, modes and turn go on the first trainer card, as in 008. Doubles stack two battler cards on each side of the VS. "Show unrevealed opponent Pokémon" is off by default. With it off, unrevealed opponent tiles stay in place as `?` tiles with a ball icon and no species, level or HP. The tile count matches the party-size balls the game itself shows. With it on, the tiles render like revealed ones. The setting is stored in localStorage. The URL query `?showUnrevealed=1` or `=0` overrides it for that page load without writing to storage, so OBS browser sources can set it. "Pokémon left" is derived per trainer from `opponent.party` as the count of mons with HP above 0, revealed or not. That matches the game's own ball indicator. Field conditions show only as badges for active effects. `none` and `null` values are hidden. The status-block note lists the battle fields the running generation lacks.

The single shape keeps singles and doubles in one schema. The `null` versus `"none"` split keeps the 006 null rule honest. `revealed` lets the API expose everything readable while the viewer stays spoiler-safe for streams. `lastBattle` with `battleId` gives Nuzlocke trackers one outcome per encounter without a history resource.

Excluded: singles-only `playerMon`/`opponentMon` fields, emitting active data with nulls during the battle intro, a validation timeout, hiding unrevealed mons from the API, a reduced opponent mon schema, inferring caught from party diffs, a separate battle history resource, raw battle type bits, counting turns in the program, a "Pokémon left" field, volatile statuses and CFRU rooms in v2.0, and a card footnote for missing weather.
