# Bridge wire protocol

## Question

What do the program and the mGBA and BizHawk Lua bridges say to each other over the socket?

Decide the transport and default port per bridge, message framing, the hello (bridge name, bridge protocol version as an integer separate from the app version, emulator and version, and the game code and CRC32 where the emulator gives them), the read request shape (batched domain, offset and length, per [Emulator memory access APIs](./001-emulator-memory-access.md)), error replies, and how the adapter treats a bridge that sends no hello or a different protocol version. Bridge reply validation uses Zod in `server/`, per [Importable package for overlay developers](./015-importable-package.md).

Input from [Release pipeline](./017-release-pipeline.md): the adapter refuses a protocol mismatch, and a bridge with no hello is reported as an unknown bridge. In both cases `status` lets the viewer tell the user to reload the bridge from the data-folder path or the `/bridges/<name>.lua` download. The protocol integer bumps only on wire changes.

Input from [Read loop and latency budget](./018-read-loop.md): the read request is a list of ranges answered in one reply from one logical sample. Every request carries an id the reply echoes, and the adapter discards a late reply that arrives after its 250 ms timeout. A bridge keeps its socket open while the emulator is paused, and a closed socket is the only disconnect signal for mGBA and BizHawk, as the read loop answer states.

Input from [Config file](./019-config-file.md): each bridge's endpoint is a setting, `adapters.mgba` and `adapters.bizhawk` with `host` (default `127.0.0.1`) and `port`. This ticket sets the two default ports. They must differ from each other, from the app's default 7425 and from RetroArch's 55355.

## Answer

Each bridge is a TCP server, and the program connects to it. Every message is a length-prefixed binary frame. Reads and their data are raw binary, and the control messages carry a JSON body. A bridge sends a hello on every connection, then a game message, and sends the game message again on every ROM change. This is bridge protocol 1.

- **Transport.** Both bridges use TCP. The bridge listens and the program connects, which matches adapter probing and the `adapters.<name>.host`/`port` settings. mGBA uses its built-in `socket` API. BizHawk uses LuaSocket (`require("socket")`), which the v1 script in this repo (`network/http_server.lua`) and Archipelago's BizHawk connector (see the [research asset](../assets/001-emulator-memory-access.md)) both use as a TCP server.
- **Ports.** By default mGBA listens on 7426 and BizHawk on 7427, next to the app's 7425. The program never probes v1's port 8080.
- **Bridge settings.** The program writes the configured `host` and `port` into each bridge, both in the data-folder copy and in the file it serves at `/bridges/<name>.lua`. The bridge binds to that host. For the two bridge adapters, `host` must be an IPv4 or IPv6 literal, so the bridge binds to exactly the address the program connects to and never resolves a name. The settings schema rejects hostnames there, and also the wildcard addresses `0.0.0.0` and `::`, because the program connects to `host` and a wildcard bind would open the bridge on every interface. For a remote setup, the user sets `host` to the emulator machine's address and loads the bridge on that machine, which exposes read-only memory access on that network, as the LAN note in [App form factor](./003-app-form-factor.md) already documents for the API. The program rewrites a data-folder bridge whenever the generated file differs from the one on disk, which covers both version and settings changes. Release-asset copies carry the defaults, `127.0.0.1` and the default port. After a host or port change, nothing listens on the new endpoint until the user reloads the bridge. The adapter is then disconnected, and the viewer shows the connection screen's install steps, which begin with loading or reloading the bridge from this program's data folder. That one message covers a first install and a settings change.
- **Frames.** Every frame is `u32 length | u8 kind | u32 id | body`, with integers in big-endian order. `length` counts every byte after the length field. Kinds and body encodings:

  | Kind | Value | Direction | Body | Largest body |
  |---|---|---|---|---|
  | `HELLO` | 1 | bridge to program | JSON | 4 KiB |
  | `GAME` | 2 | bridge to program | JSON | 4 KiB |
  | `READ` | 3 | program to bridge | binary | 4,610 bytes (512 ranges) |
  | `DATA` | 4 | bridge to program | binary | 64 KiB |
  | `ERROR` | 5 | bridge to program | JSON | 4 KiB |

  A frame whose `length` exceeds its kind's largest body plus the 5 header bytes, or whose kind is unknown, is a bad frame. The receiver doesn't wait for the rest of it. Messages the bridge sends unprompted use id 0. Request ids start at 1 on each connection, go up by one and skip 0 when they wrap. A reply carries the id of the request it answers.
- **Hello.** The bridge sends it unprompted as the first frame on every connection, including connections it then refuses. The JSON body is `{ bridge: "mgba" | "bizhawk", protocol: 1, build: string, emulator: { name: string, version: string | null } }`. `build` is the app version the bridge came from. It appears in logs and in `status.adapter.bridge` for diagnosis, and never affects compatibility. Only `protocol` decides compatibility, and it changes only when the wire changes.
- **Game message.** The bridge sends it right after the hello and again whenever a ROM loads, unloads or changes. The JSON body is `null` when no ROM is loaded. Otherwise it is `{ platform: "gb" | "gba" | "other", romName: string | null, crc32: string | null, sha1: string | null, domains: { [name]: size } }`. Hashes are lowercase hex. The mGBA bridge fills `crc32` from `emu:checksum(C.CHECKSUM.CRC32)`. The BizHawk bridge fills `sha1` from `gameinfo.getromhash()`, with any `SHA1:` prefix stripped, only for cores the bridge spike confirmed return a SHA-1, and sends null for every other core. Profiles already hold `crc32` and `sha1` lists, and identification matches on whichever hash the emulator sent, per [Game identification](./009-game-identification.md). `romName` appears only in logs. The game code and title come from the program's own header read. A game message is how the adapter reports a ROM change, which triggers re-identification. The bridge sends it before it answers any read on the new ROM, and the adapter drops every reply to a request it sent before that game message arrived. `platform: "other"`, a BizHawk system outside GB, GBC and GBA, leaves the ROM unidentified.
- **Memory domains.** Both bridges use one set of domain names on the wire, each with a fixed u8 code. GBA has `rom` (1), `ewram` (2) and `iwram` (3). GB and GBC have `rom` (1), `wram` (4), `hram` (5) and `sram` (6). `rom` is the whole ROM image, addressed by file offset. GB `wram` is linear across the CGB banks, so bank n starts at offset n × 0x1000. `sram` is cartridge RAM, which Gen 1-2 boxes need. Each bridge maps these names to its emulator's own domains, so the program has one bridge adapter, configured by bridge name and endpoint. Decoders, profiles and fixtures use the same names. If a shim can reach only part of a domain, such as only the mapped WRAM banks, the game message reports the size it can reach, and the range checks below fail only the decoders that need the rest.
- **Reads.** A `READ` body is a `u16` range count followed by `u8 domain | u32 offset | u32 length` for each range. The `DATA` body is the bytes of every range in request order, with nothing between them, since the request already gives each length. The bridge reads every range in one script callback, so one reply is one sample. A request holds at most 512 ranges and 64 KiB of data. The adapter splits only `rom` reads larger than that, such as name tables at identification, because ROM doesn't change between requests. It never splits a read of a RAM domain. The Gen 3 PC storage read, about 33.6 KB for all 14 boxes, fits in one request. A test checks that each decoder's declared RAM reads fit the caps. The wire carries only direct ranges, with no pointer ranges.
- **Range checks.** Before sending, the adapter checks each range against the domain sizes from the game message. It drops a bad range and fails only the decoders that asked for it. The bridge checks again and answers a request with any bad range with one error for the whole request.
- **Replies the adapter can't use.** An `ERROR` with id 0 answers no request, so the adapter routes it by code: `busy` sets that problem, and `bad_frame` is logged before the bridge closes the connection. Otherwise the adapter logs and drops a `DATA` or `ERROR` whose id matches no pending request, and a `DATA` body whose length differs from the sum of the requested lengths. A dropped reply gives that cycle no data, and the connection stays open. A dropped reply that carried the pending request's id still frees the in-flight slot.
- **One request in flight.** The adapter keeps at most one unanswered request per connection. While a request is within its 250 ms timeout, the cycle waits for it, and ticks that pass are skipped as an overrunning cycle, per the read loop. After the timeout the cycle ends as a timeout, but the request still counts as unanswered until its late reply arrives, and the adapter discards that reply. Each tick that comes while a timed-out request is still unanswered sends nothing and counts as a timeout. A pause therefore never queues requests in the bridge. The bridge runs its whole step under `pcall`: accepting, receiving, framing, dispatch and the request handlers. An error inside a request handler answers that request with `internal`. An error anywhere else in the step makes the bridge log it and close the client connection, so the adapter sees a close and reconnects. A request therefore goes unanswered on an open socket only while the emulator doesn't run scripts, such as when it is paused or hung, and `stalled` shows that.
- **Errors.** An `ERROR` body is `{ code, message }`, with the id of the failed request or 0. The codes are:
  - `bad_frame`: the bridge can't parse a frame. It sends this error, then closes the connection.
  - `busy`: a second client connected. The bridge sends this error, then closes that connection.
  - `no_game`: a read arrived with no ROM loaded. The adapter treats it like a null game message.
  - `bad_range`, `too_large` and `unknown_kind`: program bugs. `unknown_kind` means a known kind sent in the wrong direction, such as `DATA` sent to the bridge, and the connection stays open. A kind value outside the table is a bad frame.
  - `internal`: a Lua error caught by `pcall`, with its text in `message`. The bridge truncates `message` so the body fits the 4 KiB cap.

  The adapter logs program bugs and internal errors at most once a minute per code, and that cycle gets no data. Errors never count toward `stalled`, which stays a timeout signal. The adapter treats an error code it doesn't know as `internal`.
- **Hello handling.** The 3 s hello timer starts on each new connection. If no hello arrives in time, the adapter reports `unknown_bridge` but keeps the socket open, and a late hello clears the problem, which covers a paused emulator that answers only after unpause. The adapter checks a hello in two steps. First it needs a JSON object with a string `bridge` and an integer `protocol`. If `protocol` differs from the program's, the adapter reports `protocol_mismatch` and sends nothing, and the connection follows the rule under One client. A protocol difference always wins over the second step, so a newer bridge whose hello changed shape is still a mismatch. Only a hello with the program's protocol goes through the full schema. Before a valid hello, any failure is `unknown_bridge`: the first frame isn't a hello, a frame doesn't parse, or the hello fails either step. The adapter then closes the socket and reconnects with backoff. A hello whose `bridge` differs from the endpoint's adapter, such as `mgba` answering on `adapters.bizhawk`, is also `unknown_bridge`. That hello passed both steps, so the adapter copies it into `status.adapter.bridge` and the viewer can name the bridge that answered and point at the port settings. The adapter logs it, sends no reads, closes the socket and retries with backoff. After a valid hello, a failure is a bridge bug, reported as `bridge_error`. A frame that doesn't parse closes the socket, since the stream can't be trusted after it, and the adapter reconnects with backoff. A game body that fails validation leaves the socket open with no reads, because no ROM can be identified without it. The next valid game message on that socket clears `bridge_error`, and reads resume. On a new connection, a valid hello and game message clear it. An error body that fails validation counts as `internal`, and the connection carries on. A refused TCP connect is not a problem. It means no bridge is listening, so the adapter stays disconnected and retries, and the viewer's connection screen shows the install steps from [Release pipeline](./017-release-pipeline.md).
- **One client.** A bridge serves one connection at a time. It sends the hello to every new connection, so probes learn which bridge answered. A second connection then gets `busy` and is closed. The program closes each probe connection right after the hello, whatever the hello says, unless that adapter becomes the live one. It never probes the endpoint it is already connected to. There is one exception. While no adapter is usable and the bridge that `status.adapter` describes has `protocol_mismatch`, the program keeps that one connection open and idle. A bridge reload then shows up as a close, and the program reconnects at once without filling the emulator console. A switch to that adapter reuses the open connection. `busy` therefore means another program instance holds the bridge, and switching adapters in the viewer never meets the program's own probe.
- **Status.** This amends [API v2 contract](./006-api-contract.md). `status.adapter` gains `bridge`, the hello body or `null` (RetroArch, or no hello yet). For `protocol_mismatch`, `bridge` holds only the step-1 fields, `bridge` and `protocol`, with `build` and `emulator` null, and the viewer compares `protocol` with the program's to say older or newer. It also gains `problem: "unknown_bridge" | "protocol_mismatch" | "busy" | "bridge_error" | null`. The API package defines both in its schemas, with `problem` and `bridge.bridge` as listed open enums per [Importable package for overlay developers](./015-importable-package.md). A bridge with any of these problems is not usable. Probing chooses only among usable adapters, so a usable adapter that responds becomes the live one, and the problem bridges show in the viewer's adapter list. A bridge that becomes usable later, such as after a late hello, doesn't replace the live adapter, and the user can switch in the viewer. While no adapter is usable, `state` is `"disconnected"` and `status.adapter` describes the bridge with a problem that comes first in the adapter priority order from [App form factor](./003-app-form-factor.md): mGBA, then RetroArch, then BizHawk. The viewer then shows reload steps that point at this program's own data-folder copy and download, which always match its protocol. For `protocol_mismatch` it also says whether the loaded bridge is older or newer than the program.
- **Validation.** `server/` holds the wire decoders. A hand-written decoder reads frame headers and the binary bodies and checks their lengths. Zod schemas in `server/` check the hello, game and error bodies. They ignore unknown keys and unknown domain names, and reject unknown `bridge` and `platform` values. A bridge that sends the program's protocol number must use exactly these values, so an unknown value is a bridge bug. The API package, not `server/`, defines the public `status.adapter.bridge` and `problem` shapes, which stay loose with open enums so clients accept values a later version adds. These are two schemas on purpose. The program copies a hello into `status` only after the strict wire check, except for a mismatch, where it copies the step-1 `bridge` string and `protocol` integer. Every value it emits therefore fits the open API shape.
- **Liveness.** A closed socket stays the only disconnect signal for the bridges, per [Read loop and latency budget](./018-read-loop.md). The adapter's socket handles the peer's close whether or not a request is pending, so it notices a bridge that unloads even when nothing is being read. The protocol has no ping message. The program turns on TCP keepalive so a remote setup notices a dead network.
- **Pause.** Each bridge answers whenever its emulator lets scripts run. The BizHawk bridge loops on `emu.yield()`, so it answers while paused if the spike below confirms that `emu.yield()` keeps scripts running then. The mGBA bridge answers from frame callbacks unless the spike below finds a way to run while paused. The program relies on neither behaviour, so `stalled` means no replies, not that the emulator is paused.
- **Bridge source.** One Lua protocol core holds the framing, dispatch, a small JSON encoder, the request checks and the protocol constant. A thin shim per emulator holds the socket calls, domain mapping, game info and callbacks. A build step joins core and shim into `mgba.lua` and `bizhawk.lua`. CI runs the core under stock Lua 5.4 with a fake shim against test vectors that the TypeScript encoder produces, and checks that the Lua and TypeScript protocol constants match. A TypeScript `FakeBridge` speaks the protocol in adapter tests. `RELEASING.md` gains a manual smoke check per emulator. Bridges need Lua 5.3 or later for `string.pack`, and they print a console message and stop if it's missing.
- **Bridge behaviour.** A bridge keeps a send buffer, because a non-blocking send can be partial. If its bind fails, it logs the port and the setting that controls it, then retries every 2 s, which covers a reload while the old socket still holds the port. It logs only that it is listening, bind errors, and the start and end of a serving session. A session starts at the first `READ` after a connect, so probes don't fill the console.

Amends [Read loop and latency budget](./018-read-loop.md). Each batch reads the pointer words for pointer-derived regions and addresses those regions with the pointer values from the previous batch that read them. If a pointer word changed, the results that used it are dropped for that cycle, and the next cycle reads the new address. Box requests follow the same rule with their own pointer. When no pointer value is known yet, such as at attach, after a game change or on a cold read, that cycle sends two requests in sequence. The first reads only the pointer words. The second reads the regions at those pointers together with the pointer words again, and the decoders use the second reply as the cycle's sample, under the same changed-pointer rule. Steady-state cycles send one request. The bridge adapters also keep at most one request in flight, as above.

Amends [Release pipeline](./017-release-pipeline.md). The program generates the bridge files with the configured host and port, and rewrites them when the generated content differs, not only when the version changes.

Amends [Config file](./019-config-file.md). `adapters.mgba.host` and `adapters.bizhawk.host` are also the bridge's bind address. They accept only IP literals, they reject wildcard addresses, and a host or port change needs a bridge reload.

Open for implementation. The bridge spikes confirm these, and each has a fallback decided here:

- Whether Linux BizHawk ships LuaSocket. If it doesn't, the docs say BizHawk on Linux is unsupported for now. The user chose this fallback in the interview, and the map's Notes record the scope. BizHawk has no macOS build at all, per [Emulator memory access APIs](./001-emulator-memory-access.md).
- Whether mGBA runs socket callbacks while paused. If it doesn't, the bridge answers only on frames.
- Whether `emu.yield()` keeps the BizHawk bridge answering while paused. If it doesn't, the bridge loops on `emu.frameadvance()` and answers only on frames.
- mGBA's GB `wram` size and banking. If mGBA can't expose every CGB bank, the shim reports the size it can reach, per the domain rule above.
- Which BizHawk cores return a SHA-1 from `gameinfo.getromhash()`. The shim sends `sha1` only for the cores the spike confirms, and null for the rest.
- Whether mGBA can rebind the port right after a script reload. If it can't, the 2 s bind retry covers it.
- Whether mGBA exposes its version to scripts. If it doesn't, `emulator.version` is null.

Binary frames keep the bridge's work per tick down to `string.pack` and a raw memory string. That matters because the bridge runs on the emulator thread, and a 33 KB box reply in base64 would cost it several milliseconds. JSON stays where the program wants extensible fields that Zod checks. Shared domain names push emulator differences into the Lua shims, so the program needs one bridge adapter. Reusing the previous cycle's pointers keeps steady-state cycles at one request, at the cost of one cycle after a warp.

Excluded: UDP, BizHawk's `comm.socketServer` client mode, newline-delimited JSON with base64, hex text lines, emulator-native names or bus addresses on the wire, pointer ranges on the wire, two requests in every cycle, per-range reply status, clamped reads, uncapped requests, splitting RAM reads, a bridge that answers only its newest request, several clients per bridge, a newest-replaces-oldest client rule, closing the held connection on a protocol mismatch, treating a mismatch as fatal until restart, hostnames and wildcard addresses as bridge hosts, hand-edited port constants, a ping message, game code and title in the game message, and probing v1's port 8080.
