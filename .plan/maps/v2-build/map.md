# V2 build

## Destination

Pokemon Memory Reader v2.0.0 is published through the release pipeline from the v2-rebuild spec. That means `RELEASING.md` passes for the `v2.0.0` tag and the program, the bridges and `@pokemon-memory-reader/api` are all released. Every feature the spec includes for v2.0 ships, and `beta` and `rc` prereleases mark the milestones on the way.

## Notes

- **This map executes.** It overrides "plan, don't do". Most tickets are `task` tickets that build a slice of v2 and merge it. Grilling, research and prototype tickets appear only where a build slice waits on a decision the spec left open.
- **The spec.** [V2 rebuild](../v2-rebuild/map.md) holds the decisions. After [Consolidated v2 spec](./tickets/001-consolidated-spec.md) resolves, build tickets cite sections of `../v2-rebuild/spec.md` and do not reread the old tickets. If the spec is wrong or silent, open a grilling ticket. Don't decide it inside a build ticket.
- **Execution.** The owner runs this map with the wayfinder-master skill. It uses `wayfinder/v2-build-master`, cut from `wayfinder/v2-rebuild-master`. Children implement with `tdd`. A ticket is done when its acceptance criteria pass in CI and the audit approves.
- **Main stays untouched.** At every batch merge, answer "Keep it on the master branch". Only the final release ticket merges to `main`.
- **Build order.** Skeleton and CI first, then a tracer: mGBA bridge, adapter, Emerald profile, Gen 3 party decoder, `/api/v2/party` and `status`, and a basic Party screen in a compiled executable. After that comes the rest of Gen 3, then RetroArch, the full viewer and icons, and `v2.0.0-beta.1`. Gen 1 and Gen 2, CFRU and hack profiles, BizHawk, the release candidate and `v2.0.0` follow, in that order.
- **No ROMs or emulators yet.** The owner has none on hand for now. AFK tickets test against synthetic buffers, the TypeScript fake bridge, and the Lua core under stock Lua. HITL tickets that need a real emulator, ROM or capture wait until the owner says they're available. Never commit a ROM or ROM bytes.
- **Tooling.** Tooling is already decided in the spec: Bun workspaces (`server/`, `viewer/`, `api/`, `internal/`, `bridges/`), `bun test`, `tsc --noEmit` strict, Biome, and `ci.yml` as defined in the release pipeline decision.
- **Bridge tests.** CI runs the shared Lua protocol core under stock Lua with a fake shim and drives it from Bun tests over TCP. Emulator shims get a HITL smoke test in the real emulator.
- Domain terms live in `/CONTEXT.md`. Keep using them.

## Decisions so far

- [Consolidated v2 spec](./tickets/001-consolidated-spec.md): `../v2-rebuild/spec.md` folds the 24 v2-rebuild tickets and their amendments into 14 numbered subsystem sections that build tickets cite as "spec §N.M", plus spikes with fallbacks (§15), a decision index (§16), and 15 open conflicts and gaps (§17) left unresolved. Each §17 item is now a grilling ticket, 013 to 027.
- [Workspace skeleton and CI](./tickets/002-workspace-skeleton-and-ci.md): Bun 1.4.2 workspace (server, viewer, api, internal, bridges) on TS 7 strict and Biome 2.6, SHA-pinned `ci.yml` green, `v1-lua` tag at 064d0a4 with the v1 tree removed, GPL-3.0-or-later app and MIT `api/`; the API package build and its CI check move to [API package build and check](./tickets/012-api-package-build-and-check.md).
- [Emulator Lua runtimes](./tickets/003-emulator-lua-runtimes.md): one core written for Lua 5.3/5.4 runs in mGBA and BizHawk if it avoids 5.5 changes, string arithmetic and `require`; shims wrap each emulator's sockets; CI uses `leafo/gh-actions-lua` with Lua 5.4.
- [How do profiles write addresses?](./tickets/013-profile-address-notation.md): profiles keep bus notation (GBA hex, and GB pret `bank:address` with a required `bank` on GB pointer entries). One `internal/` memory map converts to domain and offset at load and for pointer values at read time. Only canonical GBA ranges map, a pointer value of 0 is null, and a bad pointer fails only the decoders that use it that cycle.
- [What is the full Pokémon schema?](./tickets/016-pokemon-schema.md): [the amendment](./assets/016-pokemon-schema-amendment.md) settles every `Pokemon` field. Gen 1 `shiny` uses the Gen 2 DV rule, `Type` (with `mystery` and `fairy`), `nature` and `status` (with `toxic`) are closed enums, eggs get `isEgg` and `eggCycles`, `ball` is an item reference, Pokérus is a state enum, and met data and raw identity fields are in. One `Move` shape carries type, PP, max PP and PP Ups. Hack profiles gain required `moveData` and a `locations` name table with a new pointer name kind, which reverses spec §5.5's deferral.
- [What else does the profile schema hold?](./tickets/018-profile-schema-remainder.md): every profile has its own required `name`. `extends` inherits all but id, kind, name, identify, fixture, provenance and features, merges blocks one level deep with `null` removal, resolves parents after user replacements, and an official profile can't extend a hack. `trainerTables` entries are `{ base, count }`, and `features.boxes` defaults by kind with a fixture test for built-in hacks. Full amendment in [018-profile-schema-remainder](./assets/018-profile-schema-remainder.md).
- [Core module interfaces](./tickets/004-core-module-interfaces.md): [the interfaces doc](./assets/004-core-module-interfaces.md) and [code sketch](./assets/004-core-module-interfaces.sketch.ts) fix the shape build tickets copy, cited as "interfaces 004". The read loop owns the one request slot. Each emulator has one adapter with `probe`, `hold` and `live` modes. Decoders declare named regions and get `Bytes` slices plus one per-game lookup. A topic-keyed resource registry and one battle tracker sit between decoders and the API, and each data format owns its profile block. `dataFormat` is `gen1`/`gen2`/`gen3`/`cfru`, and `language` uses ISO 639-1 codes.
- [How are ROMs keyed and re-identified?](./tickets/014-rom-keying-and-reidentification.md): manual picks key by any emulator hash (SHA-1, else CRC32), else a header key tagged with the platform, plus RetroArch's content name when it has no hash. An opt-in `base:<profileId>` pick covers randomizer seeds. Only RetroArch re-checks, every 2 s, and the mGBA bridge stays CRC32-only. [Amendment](./assets/014-rom-keying-and-reidentification.md).
- [Where does reference data come from?](./tickets/019-reference-data-source.md): a dev-time generator takes English game text (`BULBASAUR`, `POKé BALL`), charmaps, species data and move data from pinned pret commits, keyed by data format and language, with location names keyed by `artVersion`. Growth curves are formulas in code, and v2.0 ships English only. SHA-1 comes from pret and CRC32 from the No-Intro entry with the same SHA-1. [Amendment](./assets/019-reference-data-amendment.md).
- [How is RetroArch probed, and what happens when a batch is too big?](./tickets/026-retroarch-probe-and-batch-caps.md): probe with `GET_STATUS`, wait 1 s, and count any valid reply as usable. RetroArch reads are cut at descriptor boundaries and 16 KiB, sent all at once, and all-or-nothing. Bridge caps are checked at profile load and never split at run time. [Amendment](./assets/026-retroarch-probe-and-batch-caps.md).

- [What fills the unset status and error details?](./tickets/020-status-and-error-details.md): every error body is `{ error: { code, message }, status }`, the SSE 400 uses `invalid_topics`, and a new 503 code `no_data` (checked last) covers cold reads and first box reads that get nothing. `status.rom` is null with no ROM and gains `platform`, `globalChecksum` and `contentName`, with header fields null when the header can't be read. `status.adapter` is exactly `{ id, stalled, bridge, problem }`. Decided in auto-mode. [Amendment](./assets/020-status-and-error-details.md).
- [Emerald profile and generator](./tickets/005-emerald-profile-and-generator.md): profile schemas, the registry loader, `internal/src/memory.ts` and `generate:profiles` are built. The generator reads pret symbols at pinned commit 4a73ce7, checks the SHA-1 against pret `rom.sha1`, and writes `emerald-us-1.0.json` with provenance. Signature words (gSpeciesInfo 0x1BC, gItems 0x1C8, gBattleMoves 0x1CC) come from `struct GFRomHeader` and have not been checked against a ROM. Follow-ups are tickets 029 to 031.
- [Bridge protocol core](./tickets/006-bridge-protocol-core.md): the Lua core in `bridges/` and the TypeScript codec in `server/src/adapter/bridge/` are tested against each other over real TCP through a Bun relay to the Lua harness. CI runs Lua 5.4 in `check` plus a separate Lua 5.3 job. Bridge JSON body schemas stay with [mGBA bridge and adapter](./tickets/007-mgba-bridge-and-adapter.md), and a TCP bad-frame test is ticket 032.
- [Do these text mismatches read the way the spec shows them?](./tickets/025-spec-text-mismatches.md): official profiles read no *names* from ROM but do read the header, signature words and trainer tables, and an adapter without ROM reads leaves those fields null. The battle warning fires once after 2 s of failing validation per flag-set period. `status.game.signature` has four values. Gen 1 `0xFF` ends the battle as `unknown` until its sequence fixture confirms `lost`, which adds a §12.7 marker gate and splits the outcome gate by data format. Tickets 018 and 022 replace 013's box timing and caps. Decided in auto-mode. [Amendment](./assets/025-spec-text-mismatches.md).
- [mGBA bridge and adapter](./tickets/007-mgba-bridge-and-adapter.md): the adapter has probe, hold and live modes with a two-step hello check, game epochs, batched reads, timeouts and backoff reconnect (probes keep backing off and only live resets it). The mGBA shim is untested and `checkSettings` rejects every all-zero host. An over-cap RAM read returns `timeout` and logs once a minute, per amendment 026. The decoder-fit test belongs to [Check batch caps at profile load](./tickets/030-batch-caps-at-profile-load.md), and serving the generated bridge is [ticket 033](./tickets/033-serve-generated-bridges.md). [Report](./assets/007-mgba-bridge-and-adapter-report.md).
- [Gen 3 party decoder](./tickets/008-gen3-party-decoder.md): the Gen 3 party decoder, the reference generator with generated `gen3-en.json` (412 species, 355 moves, 377 items, 77 abilities) and the `Pokemon` and `Party` schemas in `api/` are built. A bad checksum or bad egg fails the whole party, ability 0 gives `null`, personality stays unsigned, and `met.location.name` stays `null` until [Gen 3 location names reference data](./tickets/034-gen3-location-names.md) ships. [Report](./assets/008-gen3-party-decoder-report.md).

## Not yet specified

- The rest of Gen 3: player, bag, battle, and boxes resources; FireRed/LeafGreen and Ruby/Sapphire profiles; the full read loop with change detection, the `stalled` flag, SSE topics, and latest-wins queues; full identification (hash, signature, manual picks); and config and `/settings`. This waits on the tracer's code shape and on [How are ROMs keyed and re-identified?](./tickets/014-rom-keying-and-reidentification.md), [Is `battle.modes` an open enum?](./tickets/015-battle-modes-enum.md), [What shapes do `player` and `bag` have?](./tickets/017-player-and-bag-shapes.md) and [What happens to signatures for revisions the owner doesn't own?](./tickets/022-unowned-revision-signatures.md).
- The RetroArch adapter over network commands. Waits on [How are ROMs keyed and re-identified?](./tickets/014-rom-keying-and-reidentification.md) and [How is RetroArch probed, and what happens when a batch is too big?](./tickets/026-retroarch-probe-and-batch-caps.md).
- The full viewer: the five screens, the collapsible sidebar, Settings, the hidden opponent party, and icons with the `/icons` route, cache and icon packs. Waits on [Which routes serve the viewer's controls and info?](./tickets/021-viewer-control-routes.md).
- The `v2.0.0-beta.1` prerelease: the first real run of the release pipeline, per-OS archives, the update banner, and the API package on npm. Waits on [How do prereleases ship while main stays untouched?](./tickets/024-prereleases-without-main.md) and [Which licenses does the third-party allowlist accept?](./tickets/027-third-party-license-allowlist.md).
- Gen 1 and Gen 2 data formats, including Gen 1-2 boxes from SRAM. Waits on [What shapes do `player` and `bag` have?](./tickets/017-player-and-bag-shapes.md).
- CFRU and other hack profiles: name tables, species data, the `RHHEXP` refusal, and the `find-rom-tables` script. Waits on [How is the species-info layout confirmed, and does the signature still catch CFRU builds without DPE?](./tickets/023-cfru-species-layout-and-signature.md).
- The BizHawk bridge, which depends on whether the owner has a Windows machine for smoke tests. It also depends on whether BizHawk on Linux ships LuaSocket and whether its sockets poll while paused ([Emulator Lua runtimes](./tickets/003-emulator-lua-runtimes.md)).
- Fixture capture and tier-1 verification for each data format. This hangs on which of the primary ROMs the owner has (Red US 1.0, Crystal US 1.1, Emerald, FireRed and Ruby US 1.0) and on a CFRU hack. A format with no verified fixtures ships with `supported: false`.
- The release candidate, the `RELEASING.md` run for `v2.0.0`, and the merge to `main`. Waits on [What happens to signatures for revisions the owner doesn't own?](./tickets/022-unowned-revision-signatures.md).

## Out of scope

- Everything the v2-rebuild map rules out of scope: Gen 4 and later, memory writes, v1 maintenance, package-manager distribution and code signing, and expansion hacks.
- New features or API changes that the v2-rebuild spec doesn't include. Those go into a v2.x map after release.
