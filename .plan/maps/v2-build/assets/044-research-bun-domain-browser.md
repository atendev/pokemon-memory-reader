# 044 research: domain-browser in Bun (tag bun-v1.4.2)

Question: how does npm `domain-browser@4.23.0` (Artistic-2.0) reach the shipped `bun` binary and `bun build --compile` output?

## Findings

1. Source pull-in. `src/node-fallbacks/domain.js` is two lines: `import domain from "domain-browser"; export var { create, createDomain } = domain;` (https://github.com/oven-sh/bun/blob/bun-v1.4.2/src/node-fallbacks/domain.js). `src/node-fallbacks/package.json:17` has `"domain-browser": "^4.23.0"`; `src/node-fallbacks/bun.lock:81` pins `domain-browser@4.23.0` (sha512-ArzcM/II...PimjGA==). Same pin at bun-v1.4.4 (latest release seen) and on main.
2. Build and embed. `src/node-fallbacks/build-fallbacks.ts` runs `bun build --minify-syntax --minify-whitespace --target=node` per file, string-patches the output, then writes `<name>.js` and a zstd level-19 `<name>.js.zst` into the codegen dir (build-fallbacks.ts lines ~30-90). `scripts/build/codegen.ts:524-549` (`emitNodeFallbacks`) invokes it. `src/resolver/node_fallbacks.rs` (line 107: `fallback_spec!("domain", "node-fallbacks/domain.js")`; 23 specs): with cfg `bun_codegen_embed` it does `include_bytes!(BUN_CODEGEN_DIR/<path>.zst)` and lazily zstd-decompresses; otherwise it reads the `.js` at runtime via `runtime_embed_file!`. `scripts/build/rust.ts:445-456` sets `--cfg=bun_codegen_embed` for every non-debug build, so release binaries embed it (compressed, about 1 MB for all polyfills). At 1.4.2 Bun is Rust (the older Zig `@embedFile` path is gone).
3. Modification. Bun does not edit domain-browser. It only bundles it, minifies whitespace and syntax, and runs a generic string patch (`__require(` to `require(`, `import.meta.url` to `''`, `createRequire` removed, `global.process` to `require('process')`). The patch targets in build-fallbacks.ts are generic, none specific to domain. The 4.23.0 tarball `source/index.js` (62 lines) has only `// This file should be ES5 compatible` and an eslint comment. It has no `@license` or `/*!` banner and no copyright header. The Bevry copyright and Artistic text live only in `package/LICENSE.md` and the README, which are not bundled. So the built output keeps no license or copyright text (inference: normal comments are stripped, and none is a legal comment; the built artifact was not run).
4. Runtime use. `src/node-fallbacks/README.md`: "These files are not used by Bun's runtime. They are only used for `bun build --target=browser`." `src/resolver/resolver.rs:1889` looks up `NodeFallbackModules::map()` in the builtin-import branch gated by `check_package` and `self.opts.polyfill_node_globals`. A compiled app's own `node:domain` runs Bun's own implementation, `src/js/node/domain.ts` (starts with `// Import Events`, no domain-browser import). The polyfill text is in the binary's rodata but is only reachable if the app itself invokes the bundler or transpiler with browser target (e.g. `Bun.build({target:"browser"})` inside the compiled app, since the compiled executable is the full bun runtime). The code is present, but ordinary app code never runs it.
5. Platforms. Not platform-conditional: codegen `emitNodeFallbacks` and `bun_codegen_embed` apply to all non-debug builds, with no per-OS or per-arch branch seen in rust.ts or node_fallbacks.rs. Not verified by inspecting binaries for each target.
6. Newer releases and license history. Latest release seen is bun-v1.4.4 (checked 2026-11-16); its package.json and bun.lock still pin `domain-browser` `^4.23.0` / `4.23.0`, and main (5f3f8fe4) too. No sign Bun dropped it. Registry (https://registry.npmjs.org/domain-browser): 1.0.0 to 4.22.0 are MIT (4.22.0 published 2021-07-29). 4.23.0 (2023-10-31) is the first Artistic-2.0 version; 5.0.0 to 5.7.0 (latest, 2023-12-29) are also Artistic-2.0. So MIT 4.22.0 exists, but Bun's `^4.23.0` range excludes it, and no MIT release exists after it.
