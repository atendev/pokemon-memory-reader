# 060 CFRU plain Pokemon layout research

Question: does CFRU (Skeli789/Complete-Fire-Red-Upgrade) store party/box Pokemon unencrypted and unshuffled, for all CFRU builds or only Radical Red; are box Pokemon also plain; does PC layout differ from vanilla.

Sources read: local clone of https://github.com/Skeli789/Complete-Fire-Red-Upgrade at HEAD b637a27898b14e25dd24d0f69a3e302f0069deb8 (2025-01-24); pret/pokefirered src/pokemon.c at ce6406d8c2eaf46d543c8a2606de0c3cb1951982. No ROM or save bytes used.

## Findings (from CFRU source; items marked INFERENCE or UNVERIFIED are not confirmed)

1. CFRU patches the vanilla FireRed ROM to remove Pokemon encryption, shuffle, and checksum. File `bytereplacement`, section header `##Decryption##` (lines ~280-290 at HEAD), added by Skeli in commit 32d78201 "Added Decryption" (2019-02-01), reorganised 6fd0dc78 (2019-02-21). It is part of the generic CFRU repo, not a Radical Red patch. Patch addresses (BPE0/BPRE 1.0 ROM offsets):
   - 0803F906, 0803F90C, 0803F92A, 0803F930 (2-byte NOPs `C0 46`) and 0803F94C (`00 20 C0 46 C0 46`, i.e. `movs r0,#0; nop; nop`) all fall inside EncryptBoxMon (symbol `EncryptBoxMon = 0x803F8F8` in `BPRE.ld`). Reading: encryption XOR loop and checksum write are neutralised; the `movs r0,#0` is consistent with checksum forced to 0 (INFERENCE, not disassembled).
   - 0803FD94 (10 NOPs then `0B E0` = unconditional branch) is inside GetBoxMonData (`0x803FD44` in `BPRE.ld`); 0804051E (same pattern) is inside SetBoxMonData (`0x80404D0`). In pret these are the `if (field > MON_DATA_ENCRYPT_SEPARATOR)` blocks that call GetSubstruct x4, DecryptBoxMon, and compare CalculateBoxMonChecksum to boxMon->checksum (pret src/pokemon.c lines ~2985-2996 and ~3417-3429). The branch skips them. INFERENCE from address ranges, not a disassembly.
   - 08040AE6 NOP (end of SetBoxMonData region), 0804C062/0804C064/0804C13C (`00 21`, `00 24`): other checksum/decrypt call sites; not identified individually (UNVERIFIED).
2. CFRU's own `struct Pokemon` (include/pokemon.h ~line 302) is flat and unshuffled: personality, otid, nickname[10], language, sanity, otname[7], markings, backupSpecies(u16 at 0x1C, replaces checksum), unused(u16), then species, item, experience, ppBonuses, friendship, pokeball, unknown, moves[4], pp[4], EVs, contest stats, pokerus, metLocation, bitfields (metLevel/metGame/gigantamax/otGender, IVs/isEgg/hiddenAbility, ribbons). CFRU C code reads fields directly (e.g. src/evolution.c:30 `mon->species`, src/dynamax.c:237 `mon->gigantamax`), which only works if data is plain. Field order = vanilla substruct order Growth, Attacks, Condition, Misc (substruct types 0,1,2,3 in that order), i.e. what vanilla calls shuffle order 0 laid out sequentially.
3. CFRU's `struct BoxPokemon` (include/pokemon.h ~line 284) keeps the vanilla shape (u16 checksum, u16 unknown, four substruct fields in order) but the repo never shuffles/encrypts; the checksum field is neutralised by the patches above. CFRU also reuses `u16 backupSpecies` in struct Pokemon where the BoxPokemon has `checksum` (same offset 0x1C).
4. In CFRU, DecryptBoxMon/EncryptBoxMon are still declared (include/pokemon.h:695, 791-792) and `EncryptBoxMon`/`CalculateBoxMonChecksum` map to vanilla ROM addresses in BPRE.ld (0x803F8F8, 0x803E3E8), so the vanilla functions still exist but are patched to be inert/bypassed.

## PC box storage differs from vanilla (from CFRU source; hand-derived, see Open gaps)

- File `src/pokemon_storage_system.c`, header `include/new/pokemon_storage_system.h`. CFRU expands storage from 14 to 25 boxes (`TOTAL_BOXES_COUNT 25`, `ORIGINAL_TOTAL_BOXES_COUNT 14`, include/pokemon_storage_system.h) by storing box Pokemon as a `CompressedPokemon` of 0x3A = 58 bytes (header comment says 65 bytes; the struct comment says SIZE = 0x3A / 58; trust the struct).
- Box Pokemon in PC are therefore NOT 80-byte BoxPokemon in storage; they are compressed on the fly (`CreateBoxMonFromCompressedMon` / `CreateCompressedMonFromBoxMon`, src/pokemon_storage_system.c ~302-333). They are plain (no XOR, no shuffle, no checksum): the packing copies fields directly.
- 58-byte layout (derived from struct + conversion code; offsets computed by hand, UNVERIFIED against a real save): 0x00 personality u32; 0x04 otid u32; 0x08 nickname[10]; 0x12 language; 0x13 sanity/flag byte; 0x14 otname[7]; 0x1B markings; 0x1C species u16; 0x1E item u16; 0x20 experience u32; 0x24 ppBonuses; 0x25 friendship; 0x26 pokeball; 0x27-0x2B four 10-bit moves packed (move1:10, move2:10, move3:10 as u32 bitfield, move4:10 as u16 bitfield; exact bit order UNVERIFIED); 0x2C-0x31 EVs hp/atk/def/spd/spatk/spdef; 0x32 pokerus; 0x33 metLocation; 0x34 metInfo u16; 0x36 ivs u32 (packed 5 bits each + isEgg + hiddenAbility). PP is not stored (recomputed from moves + ppBonuses). Contest stats, ribbons, fateful flag, unused bytes dropped, so those are lost on deposit.
- RAM layout: boxes 1-19 contiguous at `0x2029314 + 4` (ORIGINAL_BOX_POKEMON_RAM, i.e. gPokemonStorage+4), stride 58, 30 slots/box. Box names array starts at `0x2029314 + 0x8344`; wallpapers at `+0x83C2`. Boxes 15-25 names go backwards from the original names base; wallpapers for boxes 15-25 live after box 19 data. Boxes 20-22 at `0x203CB44` (contiguous, "should end at 0x203DFA8"), boxes 23-24 at `0x2027434`, box 25 at `0x2024638`. Boxes 20-25 are in separate RAM locations, not in the original storage block.
- Save layout: `gSaveSectionOffsets` in src/save.c shows PokemonStorage still occupies 9 flash sectors (8 full 0xFF0 chunks + 0x450 tail = 0x83D0, same as vanilla 14-box PokemonStorage size), so "9 PC sectors" is the vanilla count and does not by itself show a layout change. CFRU saves extra data in "parasite" regions (0xEC4 bytes at SAVE_BLOCK_PARASITE 0x0203B174 spread over tails of sectors 0, 4, 13) and in extra flash sectors 30 and 31 (SaveSector30And31, loaded at SAVE_BLOCK_PARASITE + 0xEC4, size 0xFF0 each). Boxes 20-22's RAM address (0x203CB44-0x203DFA8) falls inside that sector 30/31 mirror (0x203C038-0x203E018): INFERENCE. Where boxes 23-25 are persisted is UNVERIFIED.
- Implication for the memory reader: the "vanilla 14-box layout not found" result is expected if PC slots are 58 bytes instead of 80; and sector 5-13 contains boxes 1-19 compressed, not 14 boxes x 30 x 80. Check: 19 boxes x 30 x 58 = 33060 bytes + 4 (currentBox/pad) fits inside 0x83D0 (33744) with room for names/wallpapers.

## Other CFRU hacks

- Pokemon Unbound (CFRU-based; source is closed, only the CFRU engine is open): third-party corroboration from pkedit (https://codeberg.org/ramenu/pkedit, HEAD 7a6b1e7c9941ff0c6aee909c2f213eb72f7272f9, 2026-03-18). `src/gba/unbound/ub_pokemon.h` class `ub_pokemon` sets `p_sbst_is_encrypted = false; p_sbst_is_shuffled = false;`, `has_checksum() -> false`, substructure order "GAEM" (Growth, Attacks, EVs/condition, Misc), and `pokeball` from growth substruct word 2 high half (matches CFRU's new `pokeball` byte). `docs/supported_games.md` lists Unbound but not Radical Red or Dark Violet. This is a secondary (community tool) source, not Skeli's; it agrees with the CFRU `bytereplacement` evidence. It handles `p_is_box_pkmn` through the same class and I did not verify how it reads PC boxes (UNVERIFIED whether it handles the 58-byte compressed box format).
- Unbound-specific code in CFRU source is gated with `#ifdef UNBOUND` (e.g. include/battle.h:131, src/battle_strings.c:135); the Decryption patch has no such gate and sits outside every `#ifdef` in `bytereplacement` (line 280; the only conditional before it, NO_GHOST_BATTLES at 159-162, is closed), and scripts/insert.py:407-418 applies `bytereplacement` to every build. So any hack built by running CFRU's insert.py inherits it.
- Radical Red: community description says it uses CFRU plus Dynamic Pokemon Expansion (pokecommunity thread https://www.pokecommunity.com/threads/pok%C3%A9mon-radical-red-v4-1.437688/, search-result snippet only, page not fetched). Radical Red source is not public (UNVERIFIED).
- Dark Violet: the premise that it is CFRU-based is NOT supported. Search results (https://www.pokecommunity.com/threads/pok%C3%A9mon-darkviolet-full-version-released.291789/page-2, snippet only) say it is built on a custom "Pokemon Saga ROM Base" by Chaos Rush. Its Pokemon data layout is UNVERIFIED and should not be assumed plain.
- Caveat: a hack could in principle ship its own ROM with different patches, since CFRU is a base the hack author builds on; no evidence found of any hack reverting the Decryption patch.

## Answer summary

- Party Pokemon: plain per CFRU source (not disassembled; the closed Radical Red build was checked only by the live test in ticket 060) (no XOR, no shuffle, checksum neutralised) for every build made with the stock CFRU insert pipeline, because the patch is unconditional in `bytereplacement` (commit 32d78201, 2019-02-01). Not Radical Red specific. Plain party layout = CFRU `struct Pokemon` in include/pokemon.h (100-byte shape; 0x1C is `backupSpecies`/unused, not a checksum).
- Box Pokemon in RAM/save PC storage (UNVERIFIED, from source only): also plain but NOT the 80-byte BoxPokemon; CFRU stores them as a 58-byte `CompressedPokemon` (no PP, no contest stats/ribbons), 25 boxes. Code paths that call GetBoxMonData on a box mon still see an 80-byte plain BoxPokemon, rebuilt on the fly.
- Extra-box storage: boxes 1-19 inside the original storage block, 20-25 elsewhere (see RAM addresses above); the 9 PC sectors match vanilla size 0x83D0.

## Open gaps (all UNVERIFIED)

1. Exact bit order of the packed 10-bit moves and exact byte offsets of the 58-byte format were hand-derived from source, not checked against a real Radical Red save.
2. Which flash sectors persist boxes 23-25 (and 20-22 beyond the sector 30/31 inference) not traced.
3. Patches at 0804C062/0804C064/0804C13C and 08040AE6, and the NOP/branch semantics, were inferred from address ranges, not disassembled.
4. Dark Violet engine unknown (appears non-CFRU); Radical Red and Unbound sources are closed, so their builds could in theory differ from stock CFRU. Only Radical Red (user's live test) and Unbound (pkedit's unencrypted/unshuffled flags) are corroborated.
5. Unbound's PC box format (58-byte compressed or not) not verified.
