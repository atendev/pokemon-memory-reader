# 014 mGBA ROM checksum types available to Lua scripts

Sub-question: which checksum types can a Lua script in mGBA get from `emu:checksum(...)` (the `C.CHECKSUM` constants table) in each released mGBA version (0.10.x, any 0.11.x or later release) and on master as of November 2026? Is SHA-1 or MD5 available to scripts, and from which release (or master only)? Does `emu:checksum()` with no argument still default to CRC32? How does mGBA compute the CRC32 it returns (whole ROM at load time, or something else, for GBA and GB)?

Research date: 2026-11-13. Primary sources only: mgba-emu/mgba tags, commits and files.

## Findings

- Tag list (`gh api repos/mgba-emu/mgba/tags`): newest numbered release is 0.10.5; the tags after it are `medusa-a1` and `medusa-a2` (pre-release tags of the next-generation line), no 0.11.x tag exists. Source: https://github.com/mgba-emu/mgba/tags
- Releases (`gh api repos/mgba-emu/mgba/releases`): newest published release is 0.10.5 (2025-03-09); 0.10.0 is 2022-10-12. No 0.11.x or later release exists as of 2026-11-13. The `medusa-a1` and `medusa-a2` tags are April 2017 alpha tags of an old branch (commits 2ab3fafe 2017-04-08, f3b5de1f 2017-04-26), not a future release. master head when checked: d58ea8a86f (2026-11-12). Sources: https://github.com/mgba-emu/mgba/releases, https://github.com/mgba-emu/mgba/commit/f3b5de1f29f24b4a1b4d03787f5f7154d635ceee
- C enum at 0.10.0 and 0.10.5 (`include/mgba/core/core.h` line 31): `enum mCoreChecksumType { mCHECKSUM_CRC32, };` only. Sources: https://github.com/mgba-emu/mgba/blob/0.10.0/include/mgba/core/core.h#L31-L33 and https://github.com/mgba-emu/mgba/blob/0.10.5/include/mgba/core/core.h#L31-L33
- C enum on master moved to `include/mgba/core/interface.h` (line 202): `mCHECKSUM_CRC32, mCHECKSUM_MD5, mCHECKSUM_SHA1`. Source: https://github.com/mgba-emu/mgba/blob/master/include/mgba/core/interface.h#L202-L206
- Lua constants table `C.CHECKSUM` is exported in `src/script/stdlib.c` via `mScriptContextExportConstants(context, "CHECKSUM", ...)`. At 0.10.0, 0.10.1, 0.10.2, 0.10.3, 0.10.4 and 0.10.5 it contains only `CRC32` (checked each tag: zero MD5/SHA1 entries). On master it contains `CRC32`, `MD5`, `SHA1`. Sources: https://github.com/mgba-emu/mgba/blob/0.10.5/src/script/stdlib.c#L118-L121 and https://github.com/mgba-emu/mgba/blob/master/src/script/stdlib.c#L226-L231
- The binding `_mScriptCoreChecksum` in `src/core/scripting.c` handles only `mCHECKSUM_CRC32` (4 bytes) at 0.10.0-0.10.5; on master it also handles `mCHECKSUM_MD5` (16 bytes) and `mCHECKSUM_SHA1` (20 bytes); an unsupported type returns `nil` (`mScriptValueNull`). Return value is a Lua string of raw bytes (`mScriptStringCreateFromBytes`), not a number and not hex. The CRC32 is byte-swapped to big-endian first ("This checksum is endian-dependent...let's just make it big endian for Lua"). Sources: https://github.com/mgba-emu/mgba/blob/0.10.5/src/core/scripting.c#L305-L326 and https://github.com/mgba-emu/mgba/blob/master/src/core/scripting.c#L349-L376
- Commits that added MD5 and SHA1 (all on master, none in the 0.10.5 tag; `gh api repos/mgba-emu/mgba/compare/0.10.5...<sha>` returns `diverged` for each, and each is an ancestor of master): `2ccfde0f33` "Core: Add MD5 hashing for ROMs" (2024-10-08), `9f5c2aa00c` "Scripting: Expose MD5 checksum" (2025-01-01), `eb781d290b` "Core: Add SHA1 hashing for ROMs" (2025-03-30), `5d7b875629` "Scripting: Add SHA1 checksum constant" (2025-03-31). The original `emu:checksum` binding is `b84a549e8c` "Scripting: Expose mCore.checksum function" (2022-05-28, before 0.10.0). Sources: https://github.com/mgba-emu/mgba/commit/9f5c2aa00c , https://github.com/mgba-emu/mgba/commit/5d7b875629 , https://github.com/mgba-emu/mgba/commit/2ccfde0f33 , https://github.com/mgba-emu/mgba/commit/eb781d290b
- CHANGES: the "0.11.0: (Future)" section on master lists "Core: Add MD5 hashing for ROMs" and "Core: Add SHA1 hashing for ROMs" (lines 81, 83); the 0.10.5 CHANGES (dated 2025-03-08) has no MD5/SHA1 entry. So MD5/SHA1 are slated for the unreleased 0.11.0. Sources: https://github.com/mgba-emu/mgba/blob/master/CHANGES#L81-L83 and https://github.com/mgba-emu/mgba/blob/0.10.5/CHANGES
- How GBA CRC32 is computed: `_GBACoreChecksum` does `memcpy(data, &gba->romCrc32, ...)`, i.e. it returns a value cached at load time, not recomputed per call. `GBALoadROM` sets `gba->romCrc32 = doCrc32(gba->memory.rom, gba->pristineRomSize)` (whole ROM file content, `pristineRomSize` = file size); `GBAApplyPatch` recomputes it over the patched ROM (`memory.romSize`); it is reset to 0 on unload. Sources: https://github.com/mgba-emu/mgba/blob/0.10.5/src/gba/core.c#L583-L591 and https://github.com/mgba-emu/mgba/blob/0.10.5/src/gba/gba.c#L450 (load) and #L547 (patch)
- How GB/GBC CRC32 is computed: `_GBCoreChecksum` also `memcpy`s the cached `gb->romCrc32`; `GBLoadROM` sets `gb->romCrc32 = doCrc32(gb->memory.rom, gb->memory.romSize)` with `romSize = pristineRomSize = vf->size(vf)` (for GBX files, the GBX footer's ROM size); `GBApplyPatch` recomputes after patching. Sources: https://github.com/mgba-emu/mgba/blob/0.10.5/src/gb/core.c#L487-L495 and https://github.com/mgba-emu/mgba/blob/0.10.5/src/gb/gb.c#L190 (load) and #L506 (patch)
- Master MD5/SHA1 are computed on demand per call, not cached at load: `_GBACoreChecksum` hashes the ROM VFile (`md5File(gba->romVf)` / `sha1File`), else the multiboot VFile, else the pristine ROM buffer (`pristineRomSize`) when unpatched, else the patched buffer (`memory.romSize`), else an empty buffer. GB does the same minus the multiboot branch. Sources: https://github.com/mgba-emu/mgba/blob/master/src/gba/core.c#L700-L734 and https://github.com/mgba-emu/mgba/blob/master/src/gb/core.c#L540-L565

## Soft patches (checked by the main thread, 2026-11-14)

- On master, `GBAApplyPatch` unmaps the ROM file when it patches but leaves `gba->romVf` set, and it recomputes `romCrc32` over the patched ROM. `_GBACoreChecksum` hashes `romVf` first in its MD5 and SHA-1 branches. So when mGBA soft-patches a ROM (a `.ips`, `.ups` or `.bps` beside it), CRC32 covers the patched ROM, but MD5 and SHA-1 cover the unpatched file. `GBApplyPatch` also unmaps without clearing `gb->romVf`. Sources: https://github.com/mgba-emu/mgba/blob/master/src/gba/gba.c (`GBAApplyPatch`), https://github.com/mgba-emu/mgba/blob/master/src/gba/core.c (`case mCHECKSUM_SHA1`), https://github.com/mgba-emu/mgba/blob/master/src/gb/gb.c (`GBApplyPatch`).
- Consequence: a bridge that sent mGBA's SHA-1 would report a soft-patched hack with its base game's hash, which is an exact match for the wrong profile. The GB SHA-1 branch on master also hashes `gb->romVf` first, so the same holds for GB. Source: https://github.com/mgba-emu/mgba/blob/master/src/gb/core.c (`case mCHECKSUM_SHA1`).
